## 1. A 层 · 契约层 Gate（写后端前必须先改接口）

### A1 · `Blob` 不得出现在跨 HTTP 的 DTO 中

- 从所有跨 HTTP 的 DTO 中**移除 `blob` 字段**；列表/元数据接口返回 `ApiResponse<...MetaDto[]>` / `ApiResponse<...MetaDto>`。
- 二进制下载（`getContactFile` / `getDemoArtifact`）改为**独立二进制流端点**，返回原始字节 + `Content-Type` + `Content-Disposition`，**不在 `ApiResponse` 内**。
- 上传（`uploadContactFiles` / `saveDemoArtifact` / `releaseDemoTestReport`）改用 `multipart/form-data`，返回 JSON 元数据。
- 契约签名同步更新；Mock adapter 与 Frappe adapter 对齐到同一签名。`MultipartFilePart` / `BinaryDownload` 是浏览器传输对象，**不得** JSON 序列化为 `ApiResponse`。
- **【验收标准】** grep `types/*.ts` 无任何跨 HTTP DTO 含 `Blob`；下载端点抓包为二进制流且带 `Content-Disposition`；上传抓包为 multipart。

### A2 · 所有业务记录必须支持乐观锁

- 每个业务记录 DTO 增加 `modified: string`（ISO 8601 带时区），Frappe 的 `modified` 直接透传。
- 每个 `update*` 方法入参增加 `expectedModified: string`（update ID 与乐观锁令牌都是方法参数，不在 payload 内）。
- 服务端以 `UPDATE ... WHERE modified = ?` 或 Frappe `doc.save()` 的 `TimestampMismatchError` 实现乐观锁；冲突抛 `CrmApiError('VERSION_CONFLICT', retryable=false)`。
- 显式区分 `artifactVersion`（DemoArtifact 内容修订，保留）≠ `modified`（记录锁，每个 DTO 都有）。
- **【验收标准】** 并发双写同一记录的集成测试，后写方收到 `VERSION_CONFLICT` 而非静默覆盖；每个业务 DTO 类型上有 `modified`。

### A3 · `owner` / `*By` 必须是稳定 ID（Link→User），不是显示名

- 所有 `owner` / `salesOwner` / `engineerOwner` / `actionOwner` / `approvedBy` / `createdBy` / `preparedBy` / `uploadedBy` / 通知 `recipientId` 建模为 **Link→User**，存稳定 `name`（email）。
- 建立显示名 → User `name` 的**受控迁移映射表**，迁移前清掉孤儿。
- 服务端**忽略客户端传入的 owner/`*By`**，统一服务端赋值（见 B1）。
- 契约层移除对客户端 `PERSONNEL` 常量的运行时依赖；按 user_id 校验角色。
- 内部员工 ID 与客户联系人 ID **不相交**（显示可重名但存储 ID 不同）；客户联系人 `演示员工14` 用 Contact DocType ID，不得解析为内部 User。
- **【验收标准】** 任意 owner 字段类型为 Link；迁移脚本对全部 owner 解析成功无 `Invalid Link`；无运行时对 `PERSONNEL` 的信任。

### A4 · 冻结错误码枚举 + 实现 Frappe 异常归一层

- 冻结第 7 节的错误码枚举作为唯一契约词表。
- `frappe-adapter` 内实现**异常归一层**：捕获 Frappe 异常 / HTTP 状态 / `fetch` 网络错误，统一抛 `CrmApiError(code, message, requestId, retryable, fieldErrors?)`。
- `denied` 集合收敛为 `{ PERMISSION_DENIED, SCOPE_DENIED }`；`NOT_PERMITTED` / `'403'` 由归一层映射到这两者。
- **【验收标准】** Frappe 抛 `PermissionError` 时前端 `denied=true`；枚举外 code 不再出现；`mapRequestError` 无死分支。

### A5 · 只读实体（Requirement / Contract / Action）必须明确写入策略

- 每个只读实体二选一并登记：
  1. 真 DocType，但写权限**锁死为脚本/导入**（`if doc.is_new() and not frappe.flags.in_import`），从权限表删除死 capability；或
  2. 外部视图/物化视图，但**必须配 ingest 通道**（ETL / 定时同步），保证 Dashboard KPI 不腐烂。
- 每个被授予的 capability 必须有对应 `assertCapability` + 方法；无 backing method 的 capability（`account_report:export`、`system:configure`、`service:write`、`procedure:*`）必须补方法或从 `ROLE_PROFILES` 删除。
- **【验收标准】** 每个只读实体已登记策略；`permissions.ts` 中无未实现的 capability；Dashboard KPI 不依赖不可变静态 seed。

### A6 · 客户端不得自造 ID；命名空间不得撞车

- 从所有 create/upsert 入参中**删除 `id?` 字段**；ID 永远由服务端决定。create 输入无主键，update 的 ID 仅作为方法参数。
- 每个 DocType 使用**独立 naming series** 或 Frappe hash 命名；迁移期旧 ID 只写 `legacy_id` 列，主键由 Frappe 生成。
- 迁移前用脚本归一化/重命名，消除 Contact 与 Contract 的 `CON-` 命名空间冲突。
- **【验收标准】** 所有 create 入参类型无 `id`；Frappe 端无人为传入主键；无两个 DocType 共享命名前缀。

## 3. 命名空间与 legacy_id 迁移

### 3.1 强制原则

1. 正常 create API **不接受** `name`/`id`/`legacy_id` 或任何客户端主键。
2. Frappe 服务端按 DocType 独立 naming series 生成 `name`；不同 DocType **不复用业务前缀**。
3. 旧 Mock ID 只写入 `legacy_id`：**不可变 / 不可做新记录外键 / 不可进正常 create/update API 寻址**。
4. `legacy_id` 在每个 DocType 内建唯一索引；跨 DocType 可有相同旧值，必须用 `(doctype, legacy_id)` 解析。
5. 所有旧外键先通过受控映射表转换为新 Frappe `name` 再写 Link；重复/孤儿/类型歧义时整批事务失败，**不允许空串或猜测目标**。
6. 导入脚本必须**幂等**：同一 `(doctype, legacy_id)` 重跑返回同一 `name`，不创建第二条。

### 3.2 独立命名空间

| 实体 / DocType | Frappe naming series | legacy 字段 |
|---|---|---|
| CRM Account | `CRM-ACC-.#####` | `legacy_id` |
| CRM Site | `CRM-SITE-.#####` | `legacy_id` |
| Contact | `CRM-CNT-.#####` | `legacy_id` |
| CRM Lead | `CRM-LEAD-.#####` | `legacy_id` |
| CRM Opportunity | `CRM-OPP-.#####` | `legacy_id` |
| CRM Opportunity Stakeholder | `CRM-STK-.#####` | `legacy_id` |
| CRM Opportunity Action | `CRM-ACT-.#####` | `legacy_id` |
| CRM Booking | `CRM-BKG-.#####` | `legacy_id` |
| CRM Visit | `CRM-VIS-.#####` | `legacy_id` |
| CRM Requirement | `CRM-REQ-.#####` | `legacy_id` |
| CRM Contract | `CRM-CTR-.#####` | `legacy_id` |
| CRM Demo Request | `CRM-DR-.#####` | `legacy_id` |
| CRM Evaluation | `CRM-EVAL-.#####` | `legacy_id` |
| CRM Test Run | `CRM-RUN-.#####` | `legacy_id` |

| CRM Contact File | `CRM-CF-.#####` | `legacy_id` |

> Contact 旧值 `CON-001` 与 Contract 旧值 `CON-001` 必须分别解析为 `Contact/legacy_id=CON-001` 与 `CRM Contract/legacy_id=CON-001`；任何仅以字符串 `CON-001` 全局查询的迁移逻辑**均不合规**。

### 3.3 受控映射表

```
source_doctype | legacy_id | target_doctype | frappe_name | imported_at | source_hash
```

- 唯一键：`(source_doctype, legacy_id)`。
- `source_hash` 检测旧 ID 源数据被悄然修改；不一致则停止并要求显式裁决。
- 映射表**不含**密码/Token/Cookie/文件正文。

**迁移顺序：** Account → Site → Contact/Lead → Opportunity → Booking/Visit/Requirement/Contract → Demo Request → Evaluation/Test Run/Artifact → Installed Tool。每批先建主记录登记映射，再解析 Link；批内任一 Link 无法解析整体回滚。

## 4. 人员身份字段与外部标签边界

### 4.1 内部身份字段（存 Frappe User `name`，本项目为 ASCII email）

`owner`、`salesOwner`、`engineerOwner`、`actionOwner`、内部 `actor`、`approvedBy`、`createdBy`、`preparedBy`、`uploadedBy`、通知 `recipientId`。

> 真实后端从 `frappe.session.user` 取当前用户，并覆盖 Actor/Approver/CreatedBy/UploadedBy 等服务端拥有字段。Mock 的 `administrator`/`sales-user`/`fae` 等值只是身份切换键，**禁止进入业务记录**。

### 4.2 不属于内部 User Link 的值（外部/组织 label）

- **客户联系人：** 使用 Contact DocType ID；如 `CON-003` 可显示"演示员工14"，但不得解析为 `person077@crm.example.invalid`。
- **外部参与者：** 如 `Customer QE`，作为外部 actor label；不得创建虚假 Frappe User。
- **组织责任主体：** 如 `Product Engineering`/`R&D Software`/`Quality`，属 team/organization label；需可分配用户时另建字段并迁移。
- **流程文案：** 如 `待安排`/`待测试`/`样片追加中`，只用于状态展示，不是 Actor ID。

### 4.3 迁移失败策略

受控映射表之外的内部人员值一律**失败关闭**：不按姓名模糊匹配、不把未知值原样写入 Link→User、不把客户联系人姓名当内部员工。部署迁移须先验证 User/Employee 存在且角色符合预期，再在单一事务内写入。

## 5. Stage 5A/5B/5C 落地的技术规范

### 5.1 响应 envelope（所有 `/api/method/rayher_crm.api.v1.*`）

```jsonc
// 成功
{ "data": {...}, "meta": { "requestId": "...", "timestamp": "ISO" }, "warnings": [] }
// 错误
{ "error": { "code": "...", "message": "...", "requestId": "...", "retryable": false, "fieldErrors": {} } }
```

- 服务端生成 `requestId` + ISO 时间戳；不泄漏 secret/session。
- Health 端点 guest-safe，只返回 status/app/version，不暴露 DB 凭据/site config/已安装用户。

### 5.2 角色与能力（服务端权威）

- 三角色：`CRM Manager` / `CRM Sales` / `CRM Engineer`；`Administrator` 映射为 Manager。
- 能力矩阵由服务端产生，匹配前端角色；普通用户必须有**恰好一个** CRM 角色，角色冲突失败关闭；客户端**不得提交**角色或 capability。
- **scope 规则：**
  - Manager = 全局；
  - Sales = **客户档案（Customer/Contact）全局可见**（同级 Sales 共享账户目录，`custom_crm_owner` 仅作写/编辑权责归属，不再做读取隔离）；Lead / CRM Opportunity / CRM Booking / CRM Demo Request / CRM Evaluation / CRM Visit / CRM Installed Tool 等业务流水仍按 `*_owner == frappe.session.user`（或账户归属）行级隔离；
  - Engineer = 只看显式 `CRM Account Engineer Assignment`；
  - `teamOwners` 已废弃，不作隐藏授权输入；
  - list 与 detail **复用同一 SQL 权限条件**；客户端 owner 字段不得扩大 scope；无/歧义 CRM 角色失败关闭。

### 5.3 DocType 映射

| 业务实体 | Frappe DocType |
|---|---|
| Account | 标准 `Customer` |
| Contact / Lead | 标准 `Contact` / `Lead` |
| Site | 标准 `Address`（Address + Customer Dynamic Link） |
| Opportunity | 自有轻量 `CRM Opportunity`（**不创建 ERPNext Company**，不触发会计/仓储） |
| Opportunity 关系 | 自有 `CRM Opportunity Stakeholder` / `CRM Opportunity Action` / `CRM Opportunity History` |
| 账号-工程师 | 自有 `CRM Account Engineer Assignment` |

### 5.4 分页 / 乐观锁 / 金额 / 日期（Stage 5B 已实现，后续强制）

- `pageSize` 范围 **1..200**，返回 `PageData` + 准确 `meta.total`；GET/list 不写库。
- 更新：`SELECT ... FOR UPDATE` 锁行 → 同事务内比 canonical `modified` → 不匹配返回 `VERSION_CONFLICT`。
- 金额正数 `DECIMAL(20,2)` + 校验 currency；数量 `INT UNSIGNED` 正整数。
- 日期真实 `YYYY-MM-DD`；timestamp 输出 **UTC ISO**。
- Lead 转换：同事务生成/复用 Customer+Contact+Opportunity，失败整体回滚，**重复提交返回同一组 ID**。
- Account/Site/Contact 名称在关联 DTO 中通过 **join 派生**，禁止复制级联名称。

### 5.5 Stage 5C 规范（Opportunity 策略）

- Opportunity stage 单一权威 8 值：`需求发现` / `技术确认` / `Demo验证` / `预算审批` / `报价` / `采购流程` / `Won` / `Lost`。
- Lead 转换填策略默认值（`需求发现`、Pipeline、score/probability=20、New Equipment、Account region、original amount）+ 一条 Lead Conversion History。
- Stakeholder/Action 删除只置 `archived=1`（软归档），DTO 隐藏，不硬删历史。
- History **只追加**，不接受客户端 actor/time；服务器写 session actor。
- Action status 仅 `Open`/`Done`；owner 不可伪造；概率/分数为 **0..100 整数**。
- Stakeholder 需 Contact↔Opportunity 同 Account；active Contact 前置要求；重复 live 关系拒绝；关系 ID 服务端生成。

## 6. 日期/时间字段类型归类

- **date-only（`YYYY-MM-DD` / MariaDB `DATE`）：** `visit.date`、`due`、`targetDate`、`customerExpectedDate`、`testRunDeadline`、`plannedEnd`、`bookingDate`、`start`、`end`、`preparedDate`、`approvedDate`。

## 7. 冻结错误码枚举（唯一契约词表）

| code | 语义 | retryable | drives denied | 收敛自 Mock 旧 code |
|---|---|:---:|:---:|---|
| `UNAUTHENTICATED` | 401，未登录/token 失效 | true | 否 | 新增 |
| `PERMISSION_DENIED` | 角色级缺权限（capability） | false | **是** | PERMISSION_DENIED |
| `SCOPE_DENIED` | 数据/记录范围越权。例外：消息为 `Sales users can only assign records to themselves.` 时，是这次写入本身的错误（Sales 把负责人选成了别人），前端按普通错误显示，不进入无权限状态（`src/api/request-state.ts`） | false | **是**（上述例外除外） | SCOPE_DENIED、INSTALLED_TOOL_SCOPE_DENIED、INSTALLED_TOOL_REASSIGN_DENIED |
| `NOT_FOUND` | 资源不存在（统一） | false | 否 | 所有 `*_NOT_FOUND` |
| `VALIDATION_ERROR` | 输入校验失败（可附 `fieldErrors`） | false | 否 | VALIDATION_ERROR、INVALID_OWNER、BOOKING_SOURCE_REQUIRED、CONTACT_INACTIVE、LINK_MISMATCH、INVALID_REPORTING_LINE |
| `CONFLICT` | 唯一性/状态锁定冲突 | false | 否 | 所有 `*_EXISTS`、`*_ALREADY_*`、`*_LOCKED`、DUPLICATE_*、CONTACT_ACCOUNT_MISMATCH、SITE_ACCOUNT_MISMATCH、CONTACT_MERGE_CONFLICT |
| `INVALID_TRANSITION` | 状态机非法流转 | false | 否 | INVALID_TRANSITION、INVALID_REPORT_STAGE、INVALID_RUN_STAGE、BOOKING_NOT_CONFIRMED、BOOKING_SOURCE_INVALID、BOOKING_STATUS_INVALID |
| `VERSION_CONFLICT` | 乐观锁冲突（见 A2） | false | 否 | 新增 |
| `REPORT_NOT_READY` | 领域业务规则不满足 | false | 否 | REPORT_NOT_READY、EVALUATION_EXISTS |
| `BACKEND_NOT_CONNECTED` | 适配器未接入 | false | 否 | — |
| `NETWORK_ERROR` | 超时/连接失败（adapter 层产出） | **true** | 否 | 新增 |
| `INTERNAL_ERROR` | 5xx，服务端异常 | **true** | 否 | 新增 |

**待裁决项（Stage 前必须二选一）：**
- `fieldErrors`：当前为死字段——前端补 `fieldErrors`→表单 binding，或从契约删除；未决定前后端可只回 `message`。
- `retryable`：当前无 UI 消费——补统一 RetryButton，或声明"仅日志、不驱动 UI"。
- `meta.staleAt` / `meta.warnings`：后端须明确 `staleAt` 语义（缓存/快照过期时刻）并在约定方法回填，否则该能力迁移后静默失效。
