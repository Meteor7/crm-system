- 日期：2026-09-15
- 适用范围：商机与 Booking 模块（Claude）、Sales Cockpit 看板（Codex）
- 依据：Codex 对齐稿 `testpr3/V2功能PRD/opportunity-cockpit-contract-alignment-2026-09-15.md` 及本方回执
- 实施批次：
  - 第 1 批：四档概率。
  - 第 2 批：七阶段、第 6/7 阶段与 Booking 入口、阶段历史、存量迁移。
- 标注"第 2 批"的内容尚未上线，上线前以本文为准。有调整时更新本文并通知看板方。
- 更新：补充第 2 批的实现细节（`stage_changed_at` 的取值、迁移行的写法、内部生产审批的撤销字段、重开规则）。

## 1. 枚举

**阶段**，存储值与展示名分离：

| 序号 | 值 | 中文 | 英文 |
|---|---|---|---|
| S1 | `qualified_opportunity` | 合格商机 | Qualified opportunity |
| S2 | `demo_done` | Demo 完成 | Demo done |
| S3 | `customer_budget_approved` | 客户预算批准 | Customer budget approved |
| S4 | `rfq_validated` | RFQ 通过 | RFQ validated |
| S5 | `quotation_sent` | 报价已发 | Quotation sent |
| S6 | `internal_validation` | 内部生产审批（可选） | Internal validation of deal |
| S7 | `po_received` | 收到 PO | PO received |
| 关闭 | `lost` | 丢单 | Lost |

- 7 个业务阶段加 `lost`，不再有 Won。
- `lost` 不是漏斗的一个阶段。

**成功概率**，从低到高：

| 值 | 中文 | 英文 |
|---|---|---|
| `low_probability` | 低 | Low probability |
| `pipeline` | 在途 | Pipeline |
| `upside` | 有望 | Upside |
| `committed` | 确定 | Committed |
| 空 | 待销售确认 | Pending sales confirmation |

- 四档不对应百分比，不计算加权金额。
- Booking 状态保持 `Pending`、`Confirmed`、`Completed`、`Cancelled`。
- 本契约新增的其他枚举（历史来源、事件、审批状态、时间依据）都用 snake_case。

## 2. 分工

- **商机方（Claude）**：商机和 Booking 的字段、状态规则、迁移，业务写接口，阶段历史和概率历史的定义与写入。
- **看板方（Codex）**：
  - 同一 Frappe 后端内的 `cockpit.*` 统计、筛选、下钻读接口；
  - Warnings 清除；
  - 目标设置及其存储；
  - 看板前端；
  - Review 上线时下线旧 Dashboard。
- **旧 Dashboard**：下线之前，商机方只做保证它不报错的最小改动。
- **历史读取**：看板服务直接读历史表，不另开 HTTP 历史接口。直接查表时，看板服务要自己校验 Manager 权限和数据范围。

## 3. 商机表字段（CRM Opportunity）

| 字段 | 类型 | 批次 | 说明 |
|---|---|---|---|
| `stage` | Select | 第 2 批 | 第 1 节的 8 个值 |
| `stage_changed_at` | Datetime | 第 2 批 | 最近一次进入当前阶段的时间，等于那条阶段历史的 `reached_at`（确认预算时是销售填写的日期） |
| `probability_level` | Select | 第 1 批 | 空或四档之一，只有商机负责人能修改 |
| `lost_at_stage` | Select | 第 2 批 | 丢单前的阶段，只会是 S1–S6。重开后清空，过去的丢单看阶段历史里的 `marked_lost` 行 |
| `lost_at` / `lost_by` | Datetime / 用户 ID | 第 2 批 | 丢单时间、操作人 |
| `budget_approved_on` | Date | 第 2 批 | 销售填写的预算批准日 |
| `legacy_stage` | Data | 第 2 批 | 迁移前的旧阶段，只读 |
| `probability`、`forecast` | — | 第 1 批停用 | 保留列但不再维护，看板不要读 |

## 4. 历史与审批表

以下各表都只追加，并与对应的业务变更在同一事务中写入。

### 4.1 阶段历史 `CRM Opportunity Stage History`（第 2 批）

| 字段 | 说明 |
|---|---|
| `name` | 事件 ID |
| `opportunity` | 商机 ID |
| `from_stage` / `to_stage` | 前后阶段。新建和迁移行的 `from_stage` 为空；丢单行 `to_stage = lost` |
| `source` | `creation` / `event` / `manual` / `approval` / `rollback` / `lost` / `migration` |
| `event` | `created`、`lead_converted`、`demo_customer_review`、`budget_confirmed`、`rfq_approved`、`quotation_published`、`internal_validation_approved`、`po_confirmed`、`marked_lost`、`rollback`、`reopened`、`migration` |
| `reference_doctype` / `reference_name` | 触发这次变更的记录，如 Evaluation、RFQ、报价版本、审批记录、Booking |
| `reason` | 回退或丢单的理由、迁移依据；不拼进阶段值 |
| `actor` | 操作人用户 ID；迁移行为 Administrator |
| `recorded_at` | 写入时间 |
| `reached_at` | 业务上到达该阶段的时间，只有迁移行可能为空 |
| `reached_at_basis` | 时间依据，取值见下方说明 |

`reached_at_basis` 的取值：

| 值 | 含义 |
|---|---|
| `recorded` | 实时操作记录的时间 |
| `declared` | 销售填写的日期 |
| `evidence` | 迁移时有凭证的时间 |
| `upper_bound` | 迁移时只能确定"不晚于"此时间 |
| `unknown` | 未知 |

迁移行的写法：
- 所有迁移行的 `source` 都是 `migration`，`from_stage` 为空，`actor` 为 Administrator。
- 已经过的里程碑各写一行凭证，`event` 用对应的事件名：`created`（由线索转化时为 `lead_converted`）、`demo_customer_review`、`budget_confirmed`、`rfq_approved`、`quotation_published`、`po_confirmed`。
- 当前阶段另写一行，`event` 为 `migration`。没有凭证时 `reached_at` 为空，`reached_at_basis` 为 `unknown`。
- 因此统计到达某阶段的次数要按 `to_stage` 计，不能只按 `event` 计。

索引：`(opportunity, recorded_at)`、`(to_stage, reached_at)`。

### 4.2 概率历史 `CRM Opportunity Probability History`（第 1 批）

| 字段 | 说明 |
|---|---|
| `name` | 事件 ID |
| `opportunity` | 商机 ID |
| `from_level` / `to_level` | 前后档位，空表示待销售确认 |
| `actor` | 操作人用户 ID |
| `changed_at` | 修改时间 |

- 索引：`(opportunity, changed_at)`。
- 新建商机时如果已设档位，会写一行 `from_level` 为空的记录。
- 降档原因和行动计划（#13）以后加列，不改动现有列。

### 4.3 内部生产审批 `CRM Opportunity Internal Validation`（第 2 批）

| 字段 | 说明 |
|---|---|
| `opportunity` | 商机 ID |
| `attempt_no` | 第几次申请 |
| `status` | `pending` / `approved` / `rejected` / `cancelled` |
| `reason` | 申请理由 |
| `expected_po_date` | 预计 PO 日期 |
| `booking_draft` | 申请时填写的 Booking 字段 |
| `requested_by` / `requested_at` | 申请人、申请时间 |
| `decided_by` / `decided_at` / `decision_comment` | 审批人、审批时间、审批意见 |
| `booking` | 批准时生成的 Booking |
| `cancelled_by` / `cancelled_at` / `cancel_reason` | 自动撤销的操作人、时间、原因。待审批的申请在确认 PO、标记丢单或阶段离开 `quotation_sent` 时撤销 |
| `live_opportunity` | 内部字段，只在 `pending` 时等于商机 ID，保证一个商机最多一条待审批申请 |

ID 格式为 `CRM-VAL-00001`，`attempt_no` 在同一商机内从 1 递增。

### 4.4 时间、历史覆盖与权限

- **时间**：库里存上海时区、不带时区的时间；接口返回 UTC ISO 格式。
- **概率历史覆盖**：从第 1 批上线起完整记录。存量商机档位为空，没有历史。
- **阶段历史覆盖**：从第 2 批迁移起完整记录。
  - 迁移前只在有凭证时写行。凭证包括：商机创建时间、Demo 进入客户评审、RFQ 批准、报价首次发布、旧历史中的手动推进和 Won。只能确定"不晚于"的时间（RFQ 创建、Booking 创建、客户意见）记为 `upper_bound`。
  - 每个商机另写一行 `migration`，记录迁移时所处的阶段。
  - 没有凭证的过去事件不倒推。
- **权限**：新表都纳入数据范围控制。通过 Frappe 通用接口只能读到自己范围内的记录。

## 5. 写接口

所有接口的共同约定：
- 调用方式：POST `/api/method/rayher_crm.api.v1.opportunities.<方法>`。
- 参数：`id`、`input`、`expectedModified`（乐观锁，必填）。
- 成功时返回商机 DTO。
- 权限：需要 `deal:write`，且商机在操作人的数据范围内；另有说明的除外。

| 方法 | 批次 | input | 规则 |
|---|---|---|---|
| `update_strategy_opportunity`（已有） | 第 1 批 | `{..., probabilityLevel}` | 只有负责人能改档位，否则返回 `PERMISSION_DENIED`。第 2 批起：从 `demo_done` 开始档位不能清空；到 `po_received` / `lost` 后冻结；不再接受直接改 `stage` |
| `confirm_budget_approved` | 第 2 批 | `{approvedOn}` | 商机须在 `demo_done`；日期不晚于今天；档位已设 |
| `request_internal_validation` | 第 2 批 | `{reason, expectedPoDate, booking}` | 商机须在 `quotation_sent`，非服务类，档位已设。没有待审批的申请，系统中另有其他在职 Manager。阶段不变，通知 Manager |
| `review_internal_validation` | 第 2 批 | `{validationId, decision, comment}` | 需要 `deal:internal_validation_approve`（目前授予所有 Manager），不能审批自己的申请。`decision` 为 `approved` 或 `rejected`，驳回时必须填意见。批准后进入 `internal_validation`，并生成 Pending Booking |
| `confirm_po` | 第 2 批 | `{booking}` | 从 `quotation_sent` 确认：新建 Confirmed Booking。从 `internal_validation` 确认：原 Pending Booking 改为 Confirmed，若它已被人工取消则新建一张。两种情况都写 `po_confirmed` 事件，reference 为 Booking ID |
| `mark_opportunity_lost` | 第 2 批 | `{lostReason}` | 只能在 S1–S6 标记；存在未取消的 Booking 时拒绝；自动撤销待审批的申请 |
| `rollback_opportunity_stage`（已有） | 第 2 批 | `{targetStage, reason}` | 只有 Manager 能操作；规则见第 6 节 |

`booking` 对象的字段：`primaryContactId`、`equipment`、`quantity`、`ddl`、`amount`、`currency`、`owner`、`note`，与现有 Booking 的必填项一致。

**第 2 批的其他规则**
- 新建商机和线索转商机时须传 `qualificationConfirmed: true`，起始阶段为 `qualified_opportunity`。
- 自动推进：
  - Demo 进入客户评审 → `demo_done`；
  - RFQ 经理批准 → `rfq_validated`；
  - 报价发布 → `quotation_sent`；
  - 已丢单的商机不会被自动推进。

## 6. S7 回退与 Booking 联动（第 2 批）

- Booking 一律由人工取消，系统不会自动取消。
- **回退或重开到 `internal_validation`**：该商机最近的一张 Booking 必须是已批准的内部生产审批生成的那张（可以已被人工取消）。它仍是 Confirmed 时，自动改回 Pending。
- **从 `po_received` 或 `internal_validation` 回退到 `quotation_sent` 或更早**：必须先人工取消 Booking。Booking 已完成（已转装机或服务已完成）时不允许回退。
- **重开已丢单的商机**：只能回退到不高于 `lost_at_stage` 的阶段（`lost_at_stage` 为空时不高于 `quotation_sent`），写 `reopened` 事件，并清空 `lost_at_stage`、`lost_at`、`lost_by` 和丢单原因。
- **撤单**：回退只追加 `rollback` 行，不删除原事件。撤单时间看 `from_stage = po_received` 的那条回退行。
- **重复确认 PO**：回退后再确认 PO 会再写一行 `po_confirmed`，同一个商机可能有多行。S7 YTD 怎么去重由看板决定。
- **补录 Booking**：商机已在 `po_received`、但 Booking 已被人工取消时，可以补录新 Booking。补录不写阶段历史，也不算新的 S7 到达。
- **Booking 页面的限制**：商机来源的 Booking 只能手动改为 Cancelled，不能改为 Confirmed，也不能恢复。
- **Booking 日期**：`booking_date` 仍是 Booking 的创建日。第 6 阶段生成的 Booking 在确认 PO 时不改这个日期。

## 7. 已知数据缺口

- **PO 数据**：本期没有实际收到 PO 的日期，也没有人民币未税金额。唯一可用的是系统确认时间，即 `po_confirmed` 行的 `reached_at`。
  - 订单金额类指标先显示"数据未就绪"。
  - S7 YTD 如果按系统确认时间统计，需要业务另行确认。
- **暂不提供**：PO 编号、PO 文件、降档原因与行动计划（#13）、丢单复盘（FR-04）。
