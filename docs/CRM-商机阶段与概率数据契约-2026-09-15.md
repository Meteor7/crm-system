## 1. 枚举

**阶段**，存储值与展示名分离：

| 序号 | 值 | 中文 | 英文 |
|---|---|---|---|
| S1 | `qualified_opportunity` | 合格商机 | Qualified opportunity |
| S2 | `demo_done` | Demo 完成 | Demo done |
| S3 | `customer_budget_approved` | 客户预算批准 | Customer budget approved |
| S4 | `rfq_validated` | RFQ 通过 | RFQ validated |
| S5 | `quotation_sent` | 报价已发 | Quotation sent |
| S6 | `internal_validation` | 内部生产审批（可选） | Internal validation of deal |
| S7 | `po_received` | 收到 PO | PO received |
| 关闭 | `lost` | 丢单 | Lost |

- 7 个业务阶段加 `lost`，不再有 Won。
- `lost` 不是漏斗的一个阶段。

**成功概率**，从低到高：

| 值 | 中文 | 英文 |
|---|---|---|
| `low_probability` | 低 | Low probability |
| `pipeline` | 在途 | Pipeline |
| `upside` | 有望 | Upside |
| `committed` | 确定 | Committed |
| 空 | 待销售确认 | Pending sales confirmation |

- 四档不对应百分比，不计算加权金额。
- Booking 状态保持 `Pending`、`Confirmed`、`Completed`、`Cancelled`。
- 本契约新增的其他枚举（历史来源、事件、审批状态、时间依据）都用 snake_case。

**区域**（已实现，区域模块 PR），与业务领域 `custom_crm_segment` 同一套机制：下拉选预设值，末尾可"＋自定义区域"。存英文名称，中文界面给预设显示中文：

| 存储值 | 中文显示 |
|---|---|
| `East China` | 华东 |
| `South China` | 华南 |
| `West China` | 华西 |
| `North China` | 华北 |
| `Central China` | 华中 |

- 本期只做国内五个预设，不设海外值。有海外客户时另行扩展并更新本文。
- 自定义区域按输入原文存储（合并多余空格），并追加进字段的共享选项，之后所有人都能在下拉中选到，所以按存储值聚合依然一致。输入如果其实是预设的变体（`华东`、`华东区`、`East`、`east-china`、首尾空格等），自动归到预设上，不新增选项；与已有自定义区域只差大小写、空格或标点的，沿用已有写法。自定义区域没有中文译名，按原文显示。
- 新的自定义区域必须用英文填写，含中文时接口返回 `VALIDATION_ERROR`，字段错误 `region: Use an English region name`。
- 选项存在 `Customer.custom_crm_region` 这个 Select 字段上，第一行留空，新建客户不会默认成华东。读取接口 `GET rayher_crm.api.v1.accounts.list_account_regions`，返回五个预设在前、自定义区域按添加顺序在后。`list_accounts` 支持 `region` 筛选，任意写法都按归一后的值匹配。
- 选项只保留五个预设和仍有客户或商机在用的自定义区域：每次 migrate 时去掉没人用的自定义区域，测试服清空工具把选项重置为五个预设。看板的区域下拉读这份选项，所以不会再出现没有数据的旧区域。
- 商机的 `subRegion` 必须是已有区域（任意写法），不会从商机上新增选项；未知区域返回 `VALIDATION_ERROR`，字段错误 `subRegion: Unknown region`。
- 存量 `Customer.custom_crm_region` 与 `CRM Opportunity.sub_region` 是自由文本，中英文混写（已见 `East China` 与 `华东` 并存）。收敛由一次迁移完成，与七阶段迁移同样的用法：
  - 预演：`bench --site <site> execute rayher_crm.setup.region_migration.dry_run`，不写库，返回每个现存取值的映射结果与客户数、商机数，逐条明细写到 `sites/<site>/private/crm-region-migration/`。
  - 执行：补丁 `normalize_crm_regions` 在升级时运行，把字段改为 Select 并写入归一后的值，不改 `modified`；重复执行不再改动。
  - 核对：`bench --site <site> execute rayher_crm.setup.region_migration.verify`，检查字段类型、五个预设都在、选项无重复写法、每个客户和商机的取值都在选项里。
  - 业务修正写在 site_config 的 `crm_region_migration_overrides`，按现存取值指定目标，例如 `{"上海": "East China"}`。不内置城市映射表：既不是预设写法、也不是英文的取值（如城市名）记为 `unmapped`，预演列出，执行时迁移停下并列出这些值，由人确认归属后写进上面的修正再执行。核对时中文选项记为错误。
  - 核对通过且销售确认预演清单后，才设置 `crm_cockpit_region_migration_verified`，看板区域筛选随之开启。
- 迁移完成前看板不要按区域聚合，同一个区域会被拆成两份。
- 看板的区域筛选以客户主档 `Customer.custom_crm_region` 为准，与市场一样取自客户主档。商机上的 `sub_region` 收敛为同一套值，但可以在商机上单独修改、可能与客户不一致，看板不用它做区域筛选。（2026-09-16 看板方确认）
- 区域不用 snake_case：自定义值是用户输入的文字，无法配出键名，预设值与它保持同一种写法。

| `lost_at_stage` | Select | 第 2 批 | 丢单前的阶段，只会是 S1–S6。重开后清空，过去的丢单看阶段历史里的 `marked_lost` 行 |

| `sub_region` | Data | 区域模块 | 取值限于第 1 节的区域选项（含自定义区域），接口写入时归一。建商机时从 `Customer.custom_crm_region` 复制；迁移前是自由文本 |

## 4. 历史与审批表

以下各表都只追加，并与对应的业务变更在同一事务中写入。

### 4.1 阶段历史 `CRM Opportunity Stage History`（第 2 批）

| 字段 | 说明 |
|---|---|
| `name` | 事件 ID |
| `opportunity` | 商机 ID |
| `from_stage` / `to_stage` | 前后阶段。新建和迁移行的 `from_stage` 为空；丢单行 `to_stage = lost` |
| `source` | `creation` / `event` / `manual` / `approval` / `rollback` / `lost` / `migration` |
| `event` | `created`、`lead_converted`、`demo_customer_review`、`budget_confirmed`、`rfq_approved`、`quotation_published`、`internal_validation_approved`、`po_confirmed`、`marked_lost`、`rollback`、`reopened`、`migration` |
| `reference_doctype` / `reference_name` | 触发这次变更的记录，如 Evaluation、RFQ、报价版本、审批记录、Booking |
| `reason` | 回退或丢单的理由、迁移依据；不拼进阶段值 |
| `actor` | 操作人用户 ID；迁移行为 Administrator |
| `recorded_at` | 写入时间 |
| `reached_at` | 业务上到达该阶段的时间，只有迁移行可能为空 |
| `reached_at_basis` | 时间依据，取值见下方说明 |

`reached_at_basis` 的取值：

| 值 | 含义 |
|---|---|
| `recorded` | 实时操作记录的时间 |
| `declared` | 销售填写的日期 |
| `evidence` | 迁移时有凭证的时间 |
| `upper_bound` | 迁移时只能确定"不晚于"此时间 |
| `unknown` | 未知 |

迁移行的写法：
- 所有迁移行的 `source` 都是 `migration`，`from_stage` 为空，`actor` 为 Administrator。
- 已经过的里程碑各写一行凭证，`event` 用对应的事件名：`created`（由线索转化时为 `lead_converted`）、`demo_customer_review`、`budget_confirmed`、`rfq_approved`、`quotation_published`、`po_confirmed`。
- 当前阶段另写一行，`event` 为 `migration`。没有凭证时 `reached_at` 为空，`reached_at_basis` 为 `unknown`。
- 因此还原某商机在某时点的阶段要按 `to_stage` 判断，不能只看 `event`：同一个阶段可能由 `migration`、`rollback` 等不同事件进入。

索引：`(opportunity, recorded_at)`、`(to_stage, reached_at)`。

### 4.2 概率历史 `CRM Opportunity Probability History`（第 1 批）

| 字段 | 说明 |
|---|---|
| `name` | 事件 ID |
| `opportunity` | 商机 ID |
| `from_level` / `to_level` | 前后档位，空表示待销售确认 |
| `reason` | 降档原因。降档必填，升档与首次设置可选 |
| `actor` | 操作人用户 ID |
| `changed_at` | 修改时间 |

- 索引：`(opportunity, changed_at)`。
- 新建商机和线索转化时档位必填，都会写一行 `from_level` 为空的记录，`actor` 是操作人——经理替销售新建或转化时就是经理。
- 已设的档位不能改回空，任何阶段都不行。只有存量商机的 `from_level` 可能为空后再被负责人首次补填，补填不算降档，不要求原因。
- 降档判定按 `low_probability < pipeline < upside < committed` 排序。新档低于旧档而 `reason` 为空时，写接口返回 `VALIDATION_ERROR`，不落库。
- `reason` 与档位改动在同一事务写入，失败一起回滚；商机详情接口在概率历史里返回该字段。
- 行动计划（#13）仍未实现，以后加列不改动现有列。

### 4.3 内部生产审批 `CRM Opportunity Internal Validation`（第 2 批）

| 字段 | 说明 |
|---|---|
| `opportunity` | 商机 ID |
| `attempt_no` | 第几次申请 |
| `status` | `pending` / `approved` / `rejected` / `cancelled` |
| `reason` | 申请理由 |
| `expected_po_date` | 预计 PO 日期 |
| `booking_draft` | 申请时填写的 Booking 字段 |
| `requested_by` / `requested_at` | 申请人、申请时间 |
| `decided_by` / `decided_at` / `decision_comment` | 审批人、审批时间、审批意见 |
| `booking` | 批准时生成的 Booking |
| `cancelled_by` / `cancelled_at` / `cancel_reason` | 自动撤销的操作人、时间、原因。待审批的申请在确认 PO、标记丢单或阶段离开 `quotation_sent` 时撤销 |
| `live_opportunity` | 内部字段，只在 `pending` 时等于商机 ID，保证一个商机最多一条待审批申请 |

ID 格式为 `CRM-VAL-00001`，`attempt_no` 在同一商机内从 1 递增。

### 4.4 时间、历史覆盖与权限

- **时间**：库里存上海时区、不带时区的时间；接口返回 UTC ISO 格式。
- **概率历史覆盖**：从第 1 批上线起完整记录。存量商机档位为空，没有历史。
- **阶段历史覆盖**：从第 2 批迁移起完整记录。
  - 迁移前只在有凭证时写行。凭证包括：商机创建时间、Demo 进入客户评审、RFQ 批准、报价首次发布、旧历史中的手动推进和 Won。只能确定"不晚于"的时间（RFQ 创建、Booking 创建、客户意见）记为 `upper_bound`。
  - 每个商机另写一行 `migration`，记录迁移时所处的阶段。
  - 没有凭证的过去事件不倒推。
- **权限**：新表都纳入数据范围控制。通过 Frappe 通用接口只能读到自己范围内的记录。自 `9035e78` 起三个 CRM 角色对业务表只有读权限，写入只能走 `api/v1` 服务。
- **历史漏斗的统计口径**（看板方确认，商机方按此提供数据）：
  - S1–S6：还原参考时点的阶段，每个商机只落入一个阶段，不累计到达次数。
  - S7 YTD：原按 `po_confirmed` 的系统确认时间；2026-09-18 起业务改为按 Booking 的实际 PO 日期归年，见第 7 节。
  - 回退行和迁移行用于还原状态，不得全部计为新增的 PO 确认。
  - 转化率已从需求中删除，不需要任何阶段的到达次数。
- **历史漏斗可还原的字段**：`CRM Opportunity History` 对每个变化的字段写一行（`field` / `from_value` / `to_value` / `actor` / `at`），覆盖更新接口涵盖的全部字段，包括 `amount`、`currency`、`original_amount`、`amount_cny`、`opportunity_owner`、`sub_region`、`tool_type`、`sale_type`，可以还原任意时点的值。Action 的增删改也记在这张表里，见 4.6。
  - 金额字段按数值比较，原样再保存不写历史（此前小数不足两位的金额，比如整数，每次保存都会多写一行 `amount` / `original_amount`，`from_value` 形如 `200000.0`，数值没有变化）。金额历史的值统一为两位小数的字符串。
  - `amount_cny` 第一次填写时 `from_value` 为空。上线补数据为每个 CNY 商机写一行，`actor` 为 `Administrator`，`at` 为上线时间，`from_value` 为空。
- **可信范围怎么判断**：最早一条历史只能证明当时存在一条记录，不能证明所有商机、所有字段自那时起都完整留痕。可信区间要结合功能上线时间、迁移记录和实际写入路径共同判断，无法证明完整的区间一律显示数据不足，不得用当前值回填。以下四种情况必定不完整：①只记变化，初始值没有行，还原要取最早一行的 `from_value`，从未改过的字段只有当前值和创建时间；②早于该表上线的区间没有任何行；③迁移前的阶段行只在有凭证时存在，可信度看 `reached_at_basis`；④绕过业务接口直接改库的数据不写历史——`9035e78` 收紧的是三个 CRM 角色的权限，Administrator 和直连 SQL 依然不留痕。

| `field` | `from_value` | `to_value` |
|---|---|---|
| `actionCreated` | 空 | 创建后的完整 Action |
| `actionUpdated` | 修改前的完整 Action | 修改后的完整 Action |
| `actionDeleted` | 空 | 被删除的 Action ID |

- Action 的 JSON 形状是 `{"id", "title", "owner", "due", "status"}`，由 `_history_value` 用 `json.dumps` 序列化后存进 `from_value` / `to_value`，读取时要解 JSON。每行都带 `actor` 和 `at`。
- **`actionUpdated` 是无条件写行的**：即使字段没有变化，一次保存也会产生一行。消费方必须比较前后值来排除无变化保存，这不是可选优化。
- `actionDeleted` 只存 Action ID，不存删除前的状态；删除是软归档（`archived = 1`），记录仍在表里。
- 因此"久未更新"应基于实质变化的行计时，删除和归档不重置计时。
- 真实历史的覆盖完整度另行核验，见 4.4 的可信范围。

## 5. 写接口

所有接口的共同约定：
- 调用方式：POST `/api/method/rayher_crm.api.v1.opportunities.<方法>`。
- 参数：`id`、`input`、`expectedModified`（乐观锁，必填）。
- 成功时返回商机 DTO。
- 权限：需要 `deal:write`，且商机在操作人的数据范围内；另有说明的除外。

| 方法 | 批次 | input | 规则 |
|---|---|---|---|
| `create_strategy_opportunity`（已有） | 档位规则、#22 | `{..., probabilityLevel, amountCny}` | 档位必填，缺失返回 `VALIDATION_ERROR`（`probabilityLevel: Required`）。不校验操作人是否为负责人：经理替销售新建时由经理设初始档位。`amountCny` 必填，大于 0、最多两位小数（`amountCny: Required` / `Invalid amount`） |
| `update_strategy_opportunity`（已有） | 第 1 批 | `{..., probabilityLevel, probabilityReason}` | 只有负责人能改档位，否则返回 `PERMISSION_DENIED`。已设档位不能改回空（`probabilityLevel: Required`）；降档时 `probabilityReason` 去除首尾空白后不能为空（`probabilityReason: Required`），原因写入概率历史，不进入商机字段历史；到 `po_received` / `lost` 后冻结；不再接受直接改 `stage`。还没有 `amountCny` 的商机，任何编辑都要带上它（`amountCny: Required`） |
| `leads.convert_lead`（已有） | 档位规则、#22 | `{..., opportunityProbabilityLevel, opportunityAmountCny}` | 档位必填，缺失返回 `VALIDATION_ERROR`（`opportunityProbabilityLevel: Required`），此时不创建任何记录。经理转化并指定其他销售为负责人时，由经理设初始档位。`opportunityAmountCny` 必填，规则同 `amountCny` |
| `confirm_budget_approved` | 第 2 批 | `{approvedOn}` | 商机须在 `demo_done`；日期不晚于今天；档位已设 |
| `request_internal_validation` | 第 2 批 | `{reason, expectedPoDate, booking}` | 商机须在 `quotation_sent`，非服务类，档位已设。没有待审批的申请，系统中另有其他在职 Manager。阶段不变，通知 Manager |
| `review_internal_validation` | 第 2 批 | `{validationId, decision, comment}` | 需要 `deal:internal_validation_approve`（目前授予所有 Manager），不能审批自己的申请。`decision` 为 `approved` 或 `rejected`，驳回时必须填意见。批准后进入 `internal_validation`，并生成 Pending Booking |
| `confirm_po` | 第 2 批、#17 | `{booking, actualPoDate}` | 实际 PO 日期必填，见本节末尾。从 `quotation_sent` 确认：新建 Confirmed Booking。从 `internal_validation` 确认：原 Pending Booking 改为 Confirmed，若它已被人工取消则新建一张。两种情况都写 `po_confirmed` 事件，reference 为 Booking ID |
| `mark_opportunity_lost` | 第 2 批 | `{lostReason}` | 只能在 S1–S6 标记；存在未取消的 Booking 时拒绝；自动撤销待审批的申请 |
| `rollback_opportunity_stage`（已有） | 第 2 批 | `{targetStage, reason}` | 只有 Manager 能操作；规则见第 6 节 |

`booking` 对象的字段：`primaryContactId`、`equipment`、`quantity`、`ddl`、`amount`、`currency`、`amountCny`、`owner`、`note`，与现有 Booking 的必填项一致。`amountCny` 只对外币订单有意义：确认 PO 时外币草稿必填（`amountCny: Required` / `Invalid amount`），申请内部审批时可以不填；人民币订单忽略它。

**实际 PO 日期（2026-09-18，#17）**
- 字段在 Booking 上：`actual_po_date`（上海日历日，客户 PO 上的日期），`actual_po_date_source`（`po_confirmation` / `booking_entry` / `backfill`），`actual_po_date_note`（最近一次经理更正的原因）。它不是商机上的 `po_date`，那个是预计 PO 日期。
- `confirm_po` 的 input 改为 `{booking, actualPoDate}`，`actualPoDate` 必填且不晚于今天（`actualPoDate: Required` / `Cannot be in the future`）。从 `quotation_sent` 新建、第 6 阶段 Pending 转 Confirmed、第 6 阶段 Pending 已取消后新建、第 7 阶段补录 Booking，四种情况都写入日期，来源 `po_confirmation`。阶段历史的 `po_confirmed` 行仍按系统时间记录。
- Upsell Booking 新建或编辑时可选填 `actualPoDate`，来源 `booking_entry`；已有日期后普通编辑不能再改（`actualPoDate: Manager correction only`），商机来源的 Booking 普通编辑也不能改。
- 补录 / 更正：`bookings.set_actual_po_date(id, {actualPoDate, reason}, expectedModified)`，只有 Manager（否则 `PERMISSION_DENIED`）；只对 Confirmed / Completed 的 Booking；已有日期时必须填 `reason`；日期不变或清空都拒绝。来源改为 `backfill`，原因写入 `actual_po_date_note`；商机来源的 Booking 同时写一行 `CRM Opportunity History`（`field = bookingPoDate`，from / to 为日期）。
- `bookings.list_bookings` 支持 `actualPoDateMissing=1`，列出缺实际 PO 日期的 Confirmed / Completed Booking。

**第 2 批的其他规则**
- 新建商机和线索转商机时须传 `qualificationConfirmed: true`，起始阶段为 `qualified_opportunity`。
- 自动推进：
  - Demo 进入客户评审 → `demo_done`；
  - RFQ 经理批准 → `rfq_validated`；
  - 报价发布 → `quotation_sent`；
  - 已丢单的商机不会被自动推进。

## 6. S7 回退与 Booking 联动（第 2 批）

- Booking 一律由人工取消，系统不会自动取消。
- **回退或重开到 `internal_validation`**：该商机最近的一张 Booking 必须是已批准的内部生产审批生成的那张（可以已被人工取消）。它仍是 Confirmed 时，自动改回 Pending。
- **从 `po_received` 或 `internal_validation` 回退到 `quotation_sent` 或更早**：必须先人工取消 Booking。Booking 已完成（已转装机或服务已完成）时不允许回退。
- **重开已丢单的商机**：只能回退到不高于 `lost_at_stage` 的阶段（`lost_at_stage` 为空时不高于 `quotation_sent`），写 `reopened` 事件，并清空 `lost_at_stage`、`lost_at`、`lost_by` 和丢单原因。
- **撤单**：回退只追加 `rollback` 行，不删除原事件。撤单时间看 `from_stage = po_received` 的那条回退行。
- **重复确认 PO**：回退后再确认 PO 会再写一行 `po_confirmed`，同一个商机可能有多行。S7 YTD 怎么去重由看板决定。
- **补录 Booking**：商机已在 `po_received`、但 Booking 已被人工取消时，可以补录新 Booking。补录不写阶段历史，也不算新的 S7 到达。
- **Booking 页面的限制**：商机来源的 Booking 只能手动改为 Cancelled，不能改为 Confirmed，也不能恢复。
- **Booking 日期**：`booking_date` 仍是 Booking 的创建日。第 6 阶段生成的 Booking 在确认 PO 时不改这个日期。
- **实际 PO 日期随 PO 走**：回退 7→6 时 Booking 改回 Pending，同时清空实际 PO 日期、来源和原因（原来有日期时写 `bookingPoDate` 历史，to 为空）；再次确认 PO 要重新填写。Booking 被人工取消时保留日期，统计按状态排除。

## 7. 已知数据缺口

- **PO 数据**：实际 PO 日期已有（`tabCRM Booking.actual_po_date`，见第 5 节），2026-09-18 之前确认的 PO 为空，显示待补录，由 Manager 补录。
- **订单人民币金额**（2026-09-18）：币种为 CNY 的订单直接用 `amount`；外币订单用 `tabCRM Booking.amount_cny`（0 表示未填）。接口 `amountCny` 已按此给出（CNY 订单等于 `amount`，外币未填为空字符串）。
  - 外币订单确认 PO 时必填；Upsell 外币订单在 Confirmed 时必填，Pending / Cancelled 可空，所以老订单取消不受阻。
  - Completed 订单不能普通编辑，外币订单的人民币金额由经理补录：`bookings.set_amount_cny(id, {amountCny, reason}, expectedModified)`，仅经理、仅 Confirmed / Completed、仅外币订单，改已有值须填原因（写入 `amount_cny_note`），商机来源的订单写一行 `bookingAmountCny` 历史。
  - `bench --site <site> execute rayher_crm.setup.booking_cny_amount.list_missing` 列出缺人民币金额的已确认 / 已完成外币订单。不自动换算，没有可信汇率。
  - 看板已按此实现（2026-09-18）：`get_review` 的 `pipeline[po].amount`、`orders.actual`、`sales[].orders` 是年累计人民币金额，只算商机来源、Confirmed / Completed、实际 PO 日期在年初至统计日的订单；`orders.series` 给出按实际 PO 日期的累计序列，页面用它画实际曲线。范围内只要有一张订单缺人民币金额，年累计金额就显示数据不足，不当 0；缺的订单在 `orders.missingAmount` 计数、`get_details(metric=po_missing_amount)` 列出，经理补录后自动恢复。
  - 业务已确认 S7 YTD 按实际 PO 日期归年，由看板方改为读 Booking：商机来源、状态 Confirmed / Completed、`actual_po_date` 落在年初到统计时点之间；缺日期的计为待补录，不猜。
- **商机人民币金额**：`amount_cny`（见第 3 节）。上线前没有这个字段；CNY 商机上线时带入 `amount`，外币商机在销售补填前为空。
  - 空值计为缺失，不是 ¥0，也不要回退到 `amount`：外币金额不能直接当人民币加总。
  - 还原过去某个时点的人民币金额：补填前的时点，原币种为 CNY 的商机用当时回放出的 `amount`（看板已按此实现），其他币种为缺失。
  - `bench --site <site> execute rayher_crm.setup.opportunity_cny_backfill.list_missing` 列出还没填的商机，交销售补。
- **暂不提供**：PO 编号、PO 文件、行动计划（#13）、丢单复盘（FR-04）。
- **设备筛选移出本期**：`CRM Opportunity.tool_type` 与 `CRM Installed Tool.model` 都是自由文本，没有受控列表，按它聚合的数字不可靠。需要时另开一轮收敛。
- **海外区域**：本期只做国内五个区域。

**关于 Test Run 的销售归属会不会漂移**：`CRM Demo Request.sales_owner` 可以修改，但只在 `EDITABLE_STATUSES = {Draft, Engineer Returned, Manager Rejected}` 三个状态下可改。Test Run 只在经理批准、生成 Evaluation 之后才存在，那时状态已不在可编辑集合内，因此**测试发生时的 `sales_owner` 就是现在读到的值**，不需要额外字段。两点提醒：批准之前的几次修改没有留痕（更新接口的历史行只记状态变化，不记 `sales_owner` 前后值），但那时还没有 Test Run，不影响归属；反过来商机负责人 `opportunity_owner` 是可改的且改动会写进商机历史，若按商机负责人归属活动必须回放历史，不能读当前值。
