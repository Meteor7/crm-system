## 1. 现状基线(一句话)

前端 Demo(Vue3 + TS + Pinia + Mock Adapter)已可作为业务演示;但当前契约层(`contracts.ts` / `types/crm.ts`)**尚未为后端准备好**:乐观锁字段缺失、`Blob` 被塞进 JSON 响应、`owner` 是显示名而非稳定 ID、错误码词表未冻结、只读实体无写入路径、create 入参接受客户端自造 ID。`backend/` 目录基本为空。这 6 项(A1–A6)是写后端代码之前的真正 Gate。

## 2. A 层 · 契约层 Gate(写后端前必须先改接口)

### A1 · `Blob` 不得出现在跨 HTTP 的 DTO 中

- **问题**:`ContactFileDto.blob`、`DemoArtifactDto.blob` 把浏览器 `Blob` 放进 `ApiResponse<T>` JSON 契约;`releaseDemoTestReport(id, { fileName, blob })` 也接收 `Blob`。JSON 无法表示 `Blob`。
- **实际例子**:Bella 给 CUSTOMER04 联系人 CON-009(演示员工35)上传 5MB 的 `FastScan规格.pdf`。Mock 把 Blob 存 IndexedDB,`getContactFile` 在 `ApiResponse` 内返回 `{ ...meta, blob }`。Frappe 实现时 `JSON.stringify({ blob })` → `{}`,下载下来是 0 字节空文件;或被迫 base64(5MB→6.7MB、不能流式、内存飙升)。
- **MUST 解决方案**:
  1. 从所有跨 HTTP 的 DTO 中**移除 `blob` 字段**;列表/元数据接口保持返回 `ApiResponse<...MetaDto[]>` / `ApiResponse<...MetaDto>`。
  2. 二进制下载(`getContactFile` / `getDemoArtifact`)**改为独立的流端点**,返回原始字节 + 正确的 `Content-Type` / `Content-Disposition`,**不在 `ApiResponse` 内**。
  3. 上传(`uploadContactFiles` / `saveDemoArtifact` / `releaseDemoTestReport`)**改用 `multipart/form-data`** 接收文件,返回 JSON 元数据。
  4. 契约签名同步更新,Mock adapter 与 Frappe adapter 对齐到同一签名。
- **【验收标准】**:grep `types/*.ts` 无任何跨 HTTP DTO 含 `Blob`;下载端点经抓包确认返回二进制流且带 `Content-Disposition`;上传经 `multipart` 抓包确认。

### A2 · 所有业务记录必须支持乐观锁

- **问题**:`updateAccount/updateBooking/updateDemoRequest/updateVisit/updateEvaluationStatus/updateInstalledTool/updateStrategyOpportunity` 签名均为 `(id, input)`,无 `version` / `modified` / `If-Match`;业务记录 DTO(Account/Contact/Lead/Opportunity/Booking/Visit/DemoRequest/Evaluation/InstalledTool/Contract)**均无锁字段**。仅 `DemoArtifactMetaDto.version` 存在,且是**内容版本号,不是乐观锁令牌**。
- **实际例子**:ACC-003(华虹宏力)的 Booking BKG-002(金额 3,600,000)。演示经理01与 Bella 同时打开编辑:演示经理01先存金额 4,200,000(v1→v2);Bella 仍停在 v1,改 ddl 后保存 → 金额被**静默覆盖回 3,600,000**,演示经理01的修改凭空消失,无人收到冲突。
- **MUST 解决方案**:
  1. 给每个业务记录 DTO 增加 `modified: string`(ISO 8601,带时区)。Frappe 的 `modified` 字段直接透传。
  2. 每个 `update*` 方法入参增加 `expectedModified: string`(或 `expectedVersion`)。
  3. 服务端以 `UPDATE ... WHERE modified = ?` 或 Frappe `doc.save()` 的 `TimestampMismatchError` 实现乐观锁;冲突时抛 `CrmApiError('VERSION_CONFLICT', retryable=false)`。
  4. 文档与字段命名**显式区分**:`artifactVersion`(DemoArtifact 内容修订,保留)≠ `modified`(记录锁,每个 DTO 都有)。
- **【验收标准】**:并发双写同一记录的集成测试,后写方收到 `VERSION_CONFLICT` 而非静默覆盖;每个业务 DTO 类型上有 `modified`。

### A3 · `owner` / `*By` 必须是稳定 ID(Link→User),不是显示名

- **问题**:所有 `owner` / `salesOwner` / `engineerOwner` / `actionOwner` / `approvedBy` / `createdBy` / `preparedBy` / `uploadedBy` 存的是 `"Demo Staff 01"` 这类显示名;唯一校验是比对客户端常量 `PERSONNEL`;而 `bootstrap.user.id` 又是 `person002@crm.example.invalid` 这种 email。两套 ID 体系并存。
- **实际例子**:迁移 ACC-001(`owner:'Demo Staff 01'`)进 Frappe,owner 字段是 Link→User,要的是 email → 写入 `'Demo Staff 01'` 抛 `Invalid Link` → **整行插入失败**。更严重:`'演示员工14'` 既是内部工程师(`personnel.ts` id `fae`),又是 CUSTOMER06 客户联系人 CON-003(`mock-data.ts`)——`personnelByName('演示员工14')` 在内部员工与客户之间歧义。
- **MUST 解决方案**:
  1. 所有 owner 类字段建模为 **Link→User / Employee**,存稳定 `name`(email 或工号)。
  2. 建立显示名→User `name` 的**迁移映射表**,迁移前清掉孤儿(如 seed 里不存在于人员目录的 owner)。
  3. 服务端**忽略客户端传入的 owner / *By**,统一服务端赋值(见 B1)。
  4. 契约层移除对客户端 `PERSONNEL` 常量的运行时依赖;`assertPersonnelRole` 改为按 user_id 校验。
  5. 裁决 `'演示员工14'` 类歧义:内部员工 ID 与客户联系人 ID 必须不相交,显示可重名但存储 ID 不同。
- **【验收标准】**:任意 owner 字段类型为 Link;迁移脚本对全部 owner 值解析成功无 `Invalid Link`;无运行时对 `PERSONNEL` 常量的信任。

### A4 · 冻结错误码枚举 + 实现 Frappe 异常归一层

- **问题**:Mock 实抛约 40 个 `code`,但前端唯一的 code 分支是 `mapRequestError` 的 `denied` 数组 `['PERMISSION_DENIED','SCOPE_DENIED','NOT_PERMITTED','403']`(后两个 Mock 从不抛)。Frappe 抛 `PermissionError`/HTTP 403 若不被翻译成 `CrmApiError(code=...)`,会落到非 CrmApiError 分支 → `denied=false`、`retryable=true`、message="数据请求失败,请稍后重试"。
- **实际例子**:工程师演示员工15(无 `account:write`)调 `createAccount`。Mock 抛 `PERMISSION_DENIED` → UI 显示"无权限"。Frappe 端若不翻译,演示员工15看到的是"请求失败,请重试",**还会一直重试,无权限态永不触发**。
- **MUST 解决方案**:
  1. 冻结第 4 节的错误码枚举表作为唯一契约词表。
  2. 在 `frappe-adapter` 内实现**异常归一层**:捕获 Frappe 异常 / HTTP 状态 / `fetch` 网络错误,统一抛 `CrmApiError(code, message, requestId, retryable, fieldErrors?)`。
  3. `denied` 集合收敛为 `{ PERMISSION_DENIED, SCOPE_DENIED }`;`NOT_PERMITTED` / `'403'` 由归一层映射到这两者后,从 `request-state.ts` 数组移除或显式标注保留理由。
  4. 同步改写 `mock-adapter.test.ts` 中对将被收敛/移除 code 的断言。
- **【验收标准】**:Frappe 抛 `PermissionError` 时前端 `denied=true`;枚举外的 code 不再出现在 mock/frappe 代码路径;`mapRequestError` 无死分支。

### A5 · 只读实体(Requirement / Contract / Action)必须明确写入策略

- **问题**:Requirement / Contract 在契约里只有只读 `list*`;`requirement:write` / `contract:write` / `system:configure` capability 被授予却**从无 `assertCapability`**(死权限)。
- **实际例子**:REQ-001(CUSTOMER06 晶圆表面缺陷检测扩容)状态停在 `'Demo验证'`,是模块级静态 `const`,从不 mutate。若 Frappe 把 Requirement 建成带角色写权限的普通 DocType(因为 capability 存在),任何人都能 `POST /api/resource/Requirement` 绕过"无写入路径"设计;若建成外部视图,REQ-001 永远卡在 `'Demo验证'`,Dashboard `requirementsByStatus` KPI **在迁移当天冻结并逐渐失真**。
- **MUST 解决方案**:每个只读实体二选一并写入本文档:
  1. 真 DocType,但写权限**锁死为脚本/导入**(`if doc.is_new() and not frappe.flags.in_import`)并从权限表删除对应死 capability;或
  2. 外部视图/物化视图,但**必须配 ingest 通道**(ETL / 定时同步),保证 Dashboard KPI 不腐烂。
  - 同步:每个被授予的 capability 必须有对应的 `assertCapability` + 方法;无 backing method 的 capability(`account_report:export`、`system:configure`、`service:write`、`procedure:*`)必须在 Stage 前补方法或从 `ROLE_PROFILES` 删除。
- **【验收标准】**:每个只读实体在本文档登记其策略;`permissions.ts` 中无未实现的 capability;Dashboard KPI 不依赖不可变静态 seed。

### A6 · 客户端不得自造 ID;命名空间不得撞车

- **问题**:`ContactInput.id?: string` 允许客户端传任意 ID,`saveContact` 里 `id = input.id ?? nextId('CON', ...)`,客户端传啥就用啥;且 Contact(`CON-001..010`)与 Contract(`CON-001..003`)**共用 `CON-###` 前缀**。
- **实际例子**:联系人 CON-001 = 演示员工36(CUSTOMER06 客户)与 演示员工116 CON-001 = CUSTOMER06 NDA 是**同 ID 不同实体**。`saveContact({ id:'CON-001', accountId:'ACC-005', ... })` 被原样接受;`saveContact({ id:'ACC-001', ... })` 也接受。迁移后 Frappe naming_series `CON-.###.` 复现不了 3 位零填充,两个 DocType 不能共享命名空间,所有 `primaryContactId==='CON-001'` 查询(如拜访 V-001)**分不清指向联系人还是演示员工116**。
- **MUST 解决方案**:
  1. 从所有 create/upsert 入参中**删除 `id?` 字段**;ID 永远由服务端决定。
  2. 每个 DocType 使用**独立 naming series** 或 Frappe hash 命名;迁移期保留旧 ID 到 `legacy_id` 列,主键由 Frappe 生成。
  3. 迁移前用脚本归一化/重命名,消除 Contact 与 Contract 的 `CON-` 命名空间冲突。
- **【验收标准】**:所有 create 入参类型无 `id`;Frappe 端无人为传入主键;无两个 DocType 共享命名前缀。

## 3. B 层 · 后端实现 MUST(Frappe / DocType / whitelisted method)

### B1 · 服务端必须丢弃客户端 `owner` / `*By`,服务端赋值

- **问题**:每个写方法的 owner/actor 是 DTO 里的普通 string,Mock 仅比对客户端 `PERSONNEL`;`createdBy`/`approvedBy` 等取自 mock 闭包 `userName`。
- **实际例子**:Alex 调 `createAccount({ name:'中芯国际', owner:'Demo Staff 02', ... })`,Mock 的 `validateOwner` 只查 Bella 是否合法 Sales,不查"Sales 只能新建给自己"。`transitionDemoRequest(manager_approve)` 写 `approvedBy = userName`——若 Frappe 从 DTO 取值,**任何角色都能演示员工106 DR-103 审批人**。
- **MUST 解决方案**:Frappe `before_insert` / `before_save` / whitelisted method 内:(1) 丢弃客户端 owner/`*By`;(2) owner 校验改为查 Frappe `User`/`Employee`/Has Role;(3) 所有 `*By` 字段一律取 `frappe.session.user`,不接受客户端值。
- **【验收标准】**:演示员工106 owner/approvedBy 的请求被服务端覆盖或拒绝;`*By` 恒等于会话用户。

### B2 · 行级隔离必须用 SQL 层 Permission Query Conditions

- **问题**:Sales 隔离靠 `canAccessAccount` 的 `account.owner === userName`(显示名)逐端点内存过滤;Manager 无条件 `return true`;Engineer 横跨 `assignedAccountIds` + `Demo.engineerOwner` + `InstalledTool.engineerOwner` 三通道且 list↔360 不一致。
- **实际例子**:任一 list 端点漏掉 `scoped()` 过滤,Alex 即可看到 Bella 的客户。Frappe 内置 `if Owner` DocPerm 比对的是 `doc._owner`(创建人 email),**不是自定义 `owner` 字段**——演示员工24(admin)创建、owner=Bella 的客户会被判给演示员工24。
- **MUST 解决方案**:
  1. owner 建模为 Link→User(见 A3),用 **Permission Query Conditions**(`tabAccount.custom_owner = %(user)s`)在 **SQL 层**强制,不用应用层 filter,不直接套 `if Owner`。
  2. Engineer 三通道统一建模:Account Engineer Assignment DocType + Demo/InstalledTool/Evaluation 的 engineerOwner Link 条件;裁决"拥有 Installed Tool 是否隐含 account-360 读",消除 list↔360 不一致。
  3. 裁决 Manager scope:`teamOwners` 当前是**死字段**(从不读取,Manager 全局可见)——要么从契约删除并确认 Manager=全局,要么先在 Mock 落地团队 scope 规则再迁移。
- **【验收标准】**:越权 list/get 在 SQL 层即被过滤(非应用层);list 与 360 可见性一致;`teamOwners` 决策已登记。

### B3 · `switchDemoIdentity` 必须在非 mock 模式禁用

- **问题**:`stores/app.ts` 的 `switchDemoIdentity` 不检查 adapter 模式,无条件 `createMockApi({ role, userName, ... })` 替换 `activeApi` 并覆写 `bootstrap.user.role`。
- **实际例子**:`VITE_API_ADAPTER=frappe` 时,devtools/测试/组件调一次 `switchDemoIdentity('sales-user')` → 真实 Frappe 会话被**静默换成客户端演示员工106的 Sales 身份**,侧边栏仍显示"本地数据库已连接"。
- **MUST 解决方案**:action 入口加 `if (!usingMock) throw` 守卫,或在非 mock 构建中移除该方法及对应 UI。UI 按钮已 `:disabled`,但 store action 必须同样不可达。
- **【验收标准】**:frappe 模式下程序化调用 `switchDemoIdentity` 抛错或不执行,`activeApi` 不变。

### B4 · 五个跨实体写入必须用单一数据库事务(且 Account 改名级联必须含 Requirement)

- **问题**:`convertLead`、`mergeContacts`、`deleteContact`、`convertBookingToInstalledTool`、`updateAccount`(改名)在 Mock 中或无回滚,或用 `Promise.allSettled` 静默吞错;`updateAccount` 改名级联**漏了 Requirement**;Contact 删除/合并会产生空串 `primaryContactId`(`''`)外键、Opportunity Stakeholder 硬删除丢历史。
- **实际例子**:把 ACC-001 改名加"上海分公司",Booking/Visit/Contract/Opportunity/InstalledTool/Demo/Evaluation 同步,但 REQ-001、REQ-002 在 `getAccount360.requirements` 与 Dashboard **仍显示旧客户名**;且无 try/catch,demo `repository.transact` 中途抛错时 sales 内存已改而 `save()` 未跑 → 列表显示新名,刷新后回退。删除某客户唯一 Active Contact 后,其 Booking 的 `primaryContactId` 变 `''` → Frappe Link 字段报 `invalid link`,整个 Booking 无法保存。
- **MUST 解决方案**:
  1. 这五个操作在 Frappe 用 `@frappe.whitelist()` + `frappe.db.transaction`(必要时 `savepoint` 链);所有子写入在同一事务,失败整体回滚;通知/文件用 `after_commit` hook。
  2. Account 改名:要么把 `accountName` 改为 join 派生的**虚拟字段**(推荐,杜绝冗余漂移),要么 `on_update` 同步所有子表(含 Requirement)且进事务。
  3. 删除/合并联系人:Link 字段允许 null 或显式"Unknown"占位;Opportunity Stakeholder 用 `disabled=1` 软删,保留审计;禁止空串 FK。
- **【验收标准】**:五操作各有"中途失败→全回滚"集成测试;改名后 Requirement 客户名同步(或为虚拟字段);无空串 FK、无硬删关键人。

### B5 · `transitionDemoRequest` 是事务实现的参考范本

- **问题/范本**:Mock 中唯一正确的是 `transitionDemoRequest`——整个状态变更 + tracking 重算 + history 追加都在单个 `repository.transact` 内。
- **实际例子**:DR-103(华虹功率器件)Engineer Review → Manager Approval,状态、tracking、history 一次性提交。
- **MUST 解决方案**:其余四个跨实体操作(B4)照此模式实现:`@frappe.whitelist()` + `frappe.db.transaction`,history/审计随主写入一起 commit。
- **【验收标准】**:四操作的事务实现与 `transitionDemoRequest` 同构(可由同一事务封装驱动)。

### B6 · GET 接口必须只读;`ensureDemoPrimaryContacts` 的写副作用必须改为迁移脚本

- **问题**:`ensureDemoPrimaryContacts`(`mock-adapter.ts`)在 `listContacts` / `getContact` / `getAccount360` / `listDemoRequests` / `listDemoWorkflows` 等**读路径**里执行 `repository.transact`(写 demoRequests)+ 改 `localContacts` + `salesRepository.save()`(写 localStorage)。读接口产生写副作用。
- **实际例子**:演示经理01打开联系人列表 → GET 触发改库;若演示员工15正编辑 DR-102,演示经理01的 GET 写覆盖演示员工15编辑(叠加 A2 无锁)。
- **MUST 解决方案**:Frappe 上 GET 绝不写数据;这种"数据自愈"改为**部署时一次性迁移脚本**或写接口内部的显式重算。GET 幂等、只读。
- **【验收标准】**:所有 `list*` / `get*` 端点在 Frappe 侧无任何写副作用(经只读连接/无 `db.set_value` 验证)。

### B7 · 产物 `version` 必须由数据库原子递增

- **问题**:`saveDemoArtifact` / `releaseDemoTestReport` 用 `Math.max(已有) + 1` 然后 push(先读后写),并发会重号。
- **实际例子**:EVAL-104(CUSTOMER05 micro-bump),演示经理01与演示员工24几乎同时点"发布外部报告",都读到 maxVersion=N、都写 N+1 → 两份 version 同为 N+1 的报告,`reportVersion` 指向最后写入者。
- **MUST 解决方案**:version 由 DB 自增列,或事务内 `SELECT ... FOR UPDATE` + 唯一约束 `(evaluation_id, type, version)`;客户端不得分配 version。
- **【验收标准】**:并发双发集成测试,两个 version 严格递增不重复;唯一约束存在。

### B8 · 日期 / 时间 wire 格式纪律

- **问题**:三个日期解析器口径不一;`getContractRisk`(`domain/contracts.ts`)把 date-only 字段当 datetime 拼接会得到 `Invalid Date → NaN → band='normal'`;`today` 硬编码 `'2026-07-17'`。
- **实际例子**:演示员工116 CON-002(CUSTOMER05 Eval Agreement,`end:'2026-09-07'`)。(a) 因 today 写死 07-17,实际今天 2026-08-04 应显示"34 天内",却显示"52 天内",**滞后 18 天**;(b) 若 Frappe 把 end 返回成 `'2026-09-07T00:00:00.000Z'`,拼接出非法串 → NaN → band='normal' → **34 天后到期的演示员工116显示"演示员工152"**,Dashboard `contractsAtRisk` 漏报。
- **MUST 解决方案**:
  1. serializer 层强制:date-only 字段一律 `YYYY-MM-DD`(MariaDB `DATE`);时间戳字段一律带时区 ISO(MariaDB `DATETIME`)。
  2. 逐字段标注类型(见下表);前端不做裸字符串比较与裸 `new Date(str)`。
  3. 所有域函数入口统一过归一化 helper(如 `shanghaiDateKey`);删除硬编码 `today`,改用服务端/系统当前日期并显式传参。
  - 字段归类:date-only = `visit.date`、`due`、`targetDate`、`customerExpectedDate`、`testRunDeadline`、`plannedEnd`、`bookingDate`、`start`、`end`、`preparedDate`、`approvedDate`;时间戳 = `createdAt`、`updatedAt`、`uploadedAt`、`lastProgressAt`、`history.at`。
- **【验收标准】**:后端返回 datetime 给 date-only 字段时,前端不崩(`getContractRisk`/`isIsoDate` 等返回合理值);无硬编码 today;跨类型排序正确。

### B9 · 分页上限 + total

- **问题**:`listInstalledTools` / `listStrategyOpportunities` / `listDemoComments` / `listControlledDocuments` / `listDemoWorkflows` 返回原始数组无 `total`;`listDemoRequests` / `listEvaluations` / `listContracts` / `listVisits` 收了 `page/pageSize` 却不切片;`pageSize` 无上限。
- **实际例子**:设备增长到几千台后 `listInstalledTools` 每次返回全量 JSON;`listVisits({ page:2, pageSize:20 })` 返回全部并标 `meta.total=N`,**翻页失效**;`listAccounts({ pageSize:100000 })` 全表返回,无 DoS 防护。
- **MUST 解决方案**:每个 list 端点强制 `limit/offset`,`pageSize` 服务端 cap(建议 ≤ 200),统一在 `meta.total` 返回总数;数组型端点改签为 `PageData`。
- **【验收标准】**:`pageSize:100000` 被截到 cap;`page:2` 返回不同数据;所有 list 有 `meta.total`。

### B10 · 金额 DECIMAL + 货币字段;数量整数

- **问题**:`OpportunityDto`/`BookingDto` 等无 `currency`(仅 StrategyOpportunity 有);`openPipeline` 不分币种相加;`quantity` 只校验 `<1` 不查整数;`amount` 不校验小数位。
- **实际例子**:OPP-003(CUSTOMER07,32,500,000,默认 CNY)与用户新建 `currency:'USD', amount:5000000` 被直接加进同一 `openPipeline` KPI;`createBooking({ quantity:2.5 })` 过校验写 INT 列报错或截断;`addEvaluationRun` 的 `wafers` 却要求整数——同项目两套口径。
- **MUST 解决方案**:货币一律 `DECIMAL(20,2)` + `currency` 字段(Link→Currency 或枚举);数量一律 `INT UNSIGNED`;serializer 校验 `amount` 小数位 ≤ 2、`quantity` 为正整数;聚合(KPI/漏斗)按币种隔离或先统一换算。
- **【验收标准】**:跨币种不混加;`quantity:2.5` 被拒;大额 `amount` 往返无精度丢失。

### B11 · 枚举单一权威 + 种子归一化

- **问题**:strategy seed 用 `'Demo 验证'`(带空格)而 legacy 联合是 `'Demo验证'`(无空格),`as` 强转 TS 抓不到;Action 终态 `'Completed'`(ActionDto)vs `'Done'`(OpportunityActionDto)两套;`OpportunityStakeholder` 的 role/influence 退化成 `string` 丢枚举。
- **实际例子**:Dashboard 漏斗按 stage 分组 → `'Demo验证'` 与 `'Demo 验证'` **变成两个独立切片**;Frappe Option 字段若只配 `'Demo验证'`,带空格的种子行被拒。
- **MUST 解决方案**:每个概念单一权威 Option 列表;迁移前脚本归一化种子值(去空格/统一终态词);明确 `OpportunityDto` 是 `StrategyOpportunityDto` 的投影视图还是独立聚合,并对齐 stage 枚举。
- **【验收标准】**:漏斗无重复切片;所有 seed stage 值 ∈ Option 列表;两套 Action 枚举关系已登记。

### B12 · 文件上传/下载的服务端校验与审计

- **问题**:上传仅靠扩展名正则;`mimeType` 直接存客户端值;Demo 产物上传完全无大小/类型/数量限制;下载 `getContactFile(fileId)` 的 scope 校验只在 Mock 里有。
- **实际例子**:演示员工15给 CON-006 上传,把 `malware.exe` 改名 `spec.pdf`、设 `mimeType:'application/pdf'` 即可通过;一次拖 500 文件无上限;Frappe 若做按 ID 直查下载,任何用户猜 fileId 即可下载他人客户文件(**IDOR**),且无下载审计。
- **MUST 解决方案**:服务端强制 MIME **魔数字节**白名单(非仅后缀)、总大小上限、单次数量上限、病毒扫描、上传时归属断言(联系人所属客户须在用户 scope 内);下载按 fileId **重新校验账户 scope** 并记录审计行。Demo 产物同样套用限制;`'External Demo Test Report PDF'` 类型只能由 `releaseDemoTestReport` 产生。
- **【验收标准】**:演示员工106类型/超大/越权下载均被拒并记审计;产物上传有大小/类型/数量限制。

### B13 · 发布的报告 PDF 不得信任客户端字节

- **问题**:外部报告 PDF 由浏览器 canvas→JPEG→PDF 栅格化生成,服务端只存字节;水印步骤为 no-op。
- **实际例子**:EVAL-104(CUSTOMER05,Customer Review,capture 96.1%)。恶意 Manager 拉取 context、把 capture 改成 99.9%、浏览器重新生成 PDF 再 POST → 服务端当权威报告存档,**无法核对字节是否匹配数据库**;且 PDF 无文本层(不可搜索/无障碍)。
- **MUST 解决方案**:服务端据**自身规范数据**(request + evaluation + runs + selection)**重新生成 PDF**;或至少存储输入数据哈希/签名校验;客户端字节仅作预览。水印必须在服务端施加。
- **【验收标准】**:篡改指标的客户端 PDF 被服务端拒绝或以服务端重生成结果为准;PDF 有文本层;水印非空。

### B14 · 通知必须有服务端事件表;frappe 模式禁用客户端 Proxy

- **问题**:`notifying-api.ts` 的 Proxy 拦截每个 API 调用,用客户端 `personnelByName` 推导收件人,写进内存 Pinia;**它也包裹未来 Frappe api**(无 `useMock` 守卫);通知数据用相对时间字符串而非 ISO,种子是硬编码假数据。
- **实际例子**:Alex 创建 DR-101(CUSTOMER06 CD 量测)指派 engineerOwner='演示员工14' → 通知只在 Alex 浏览器弹出;演示员工14打开自己浏览器**什么都看不到**(无事件表、无推送、会话不共享)。frappe 模式下 `personnelByName('演示员工14')` 对真实 Frappe user 返回 undefined → 通知只剩 `recipient:'演示员工14'` 无 recipientId → 匹配时灵时不灵。
- **MUST 解决方案**:新增服务端通知/事件 DocType(`actor`、`category`、`recipient_user`、`route`、`created_at`、`read_at`),由服务端写接口填充,经列表接口 + 已读状态暴露;通知携带服务端 ISO `created_at` 与解析后的 `recipient_user_id`(来自 Frappe User);删除硬编码种子;**frappe 模式禁用 `createNotifyingApi` Proxy**,改为订阅服务端通知。
- **【验收标准】**:跨用户/跨会话通知可达;frappe 模式下 Proxy 不产生演示员工106通知;通知时间为 ISO、收件人为 user_id。

## 4. 错误码枚举(冻结契约)

前端实际只消费 `denied` 家族;其余 code 仅作 message 文本。后端必须按下表产出 `code`、`retryable`:

| code | 语义 | retryable | drives denied | 收敛自 Mock 旧 code |
|---|---|:---:|:---:|---|
| `UNAUTHENTICATED` | 401,未登录/token 失效 | true | 否 | 新增 |
| `PERMISSION_DENIED` | 角色级缺权限(capability) | false | **是** | PERMISSION_DENIED |
| `SCOPE_DENIED` | 数据/记录范围越权 | false | **是** | SCOPE_DENIED、INSTALLED_TOOL_SCOPE_DENIED、INSTALLED_TOOL_REASSIGN_DENIED |
| `NOT_FOUND` | 资源不存在(统一) | false | 否 | 所有 `*_NOT_FOUND` |
| `VALIDATION_ERROR` | 输入校验失败(可附 `fieldErrors`) | false | 否 | VALIDATION_ERROR、INVALID_OWNER、BOOKING_SOURCE_REQUIRED、CONTACT_INACTIVE、LINK_MISMATCH、INVALID_REPORTING_LINE |
| `CONFLICT` | 唯一性/状态锁定冲突 | false | 否 | 所有 `*_EXISTS`、`*_ALREADY_*`、`*_LOCKED`、DUPLICATE_*、CONTACT_ACCOUNT_MISMATCH、SITE_ACCOUNT_MISMATCH、CONTACT_MERGE_CONFLICT |
| `INVALID_TRANSITION` | 状态机非法流转 | false | 否 | INVALID_TRANSITION、INVALID_REPORT_STAGE、INVALID_RUN_STAGE、BOOKING_NOT_CONFIRMED、BOOKING_SOURCE_INVALID、BOOKING_STATUS_INVALID |
| `VERSION_CONFLICT` | 乐观锁冲突(见 A2) | false | 否 | 新增 |
| `REPORT_NOT_READY` | 领域业务规则不满足 | false | 否 | REPORT_NOT_READY、EVALUATION_EXISTS |
| `BACKEND_NOT_CONNECTED` | 适配器未接入 | false | 否 | BACKEND_NOT_CONNECTED |
| `NETWORK_ERROR` | 超时/连接失败(adapter 层产出) | **true** | 否 | 新增 |
| `INTERNAL_ERROR` | 5xx,服务端异常 | **true** | 否 | 新增 |

- `fieldErrors`:当前为**死字段**(前端无表单字段绑定)。Stage 前二选一:前端补 `fieldErrors`→表单 binding,或从契约删除该字段。未决定前,后端可只回 `message`。
- `retryable`:前端目前**无 UI 消费**(无重试按钮、无自动重试)。Stage 前决定:补统一 RetryButton,或声明"retryable 仅供日志,不驱动 UI"。
- `meta.staleAt` / `meta.warnings`:前端 `<DataNotice v-if="meta?.stale">` 依赖,但 Mock 从不产出 `staleAt`。后端须明确 `staleAt` 语义(缓存/快照过期时刻)并在约定方法回填,否则该能力迁移后静默失效。
