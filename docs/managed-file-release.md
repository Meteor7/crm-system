# Managed File release checks

Issues #56 and #78 are handled together because ownership, native File writes and service uploads share one lifecycle.

- Contact Files use Administrator as the technical File owner; `CRM Contact File.uploaded_by` remains the human uploader. Ordinary users still need the current contact/account association and live metadata. File and metadata shares are not supported.
- The migration validates private storage and metadata references before changing targeted owners/shares. `rayher_crm.patches.v1_0.protect_contact_files.inventory` is read-only. Ambiguous references and every shared-URL alias outside canonical Contact metadata must be resolved by an operator, including older CRM aliases and folder rows that carry the same URL. A CRM module name is not proof of ownership or provenance. Metadata that points to a missing or public file blocks the migration; a File still attached to deleted Contact File metadata stays unreadable and is re-owned by Administrator. The migration does not change other app files or delete bytes.
- Native insertion/reparenting to DocTypes in the Rayher CRM module requires a server-only upload token. A client-provided `flags.ignore_permissions` is insufficient. Existing services continue to validate/scan or generate content before calling `save_private_file`. A File controller override canonicalizes same-site absolute URLs, encoded URL paths, POSIX/Windows separators, dot segments and the private `file_name` fallback before Frappe reads any referenced bytes. Ordinary content uploads and remote HTTP(S) Files, including same-site links outside `/files/` storage, keep core behavior with two deliberate differences: an upload whose bytes equal a managed blob is written to its own path instead of sharing that URL, and deleting a File row removes its own unreferenced body even when another path holds equal bytes. Existing aliases cannot change privacy, hash or URL while sharing a managed blob. A managed File's URL, privacy, hash, owner, name, attachment and folder flag change only through CRM services, and managed images cannot be optimized in place.
- Visit files require service provenance in both the CRM service and native File list/detail/private-URL paths. The download override checks current Visit access before Frappe's uploader shortcut. Older File rows did not record scans, so a meeting record or uploader is not proof. Run `rayher_crm.services.managed_file_access.reconcile_visit_files` as Administrator for inventory, then with `apply=True` to validate and scan actual bytes. The inventory lists each file's `uploader` beside the Visit's `visit_owner` and `action_owner`: a clean scan does not prove who attached a file (#78), so resolve files from unexpected uploaders before `apply=True`. Nonretryable validation rejections and missing bodies (`missing-blob`) are reported and remain inaccessible; scanner outages abort. Commit successful reconciliation and retain its output. Never mark rows verified manually.
- The CRM API serves Controlled Document source and preview bytes through `render_controlled_document`; the catalogue remains readable. Native File list/detail/export, private-URL/fid lookup, `File.get_content` reads and DocShare are denied for canonical Files, Files attached to Controlled Documents, and historical rows sharing their nonempty URL. Run `protect_controlled_document_files.inventory` first. Missing/public/remote files, wrong parents, noncanonical URLs, orphan attachments and same-URL aliases abort the migration before it changes an owner or share. A clean migration makes the technical owner Administrator and removes legacy parent/File shares; repeat runs are safe.
- Other service-managed attachments, including Status, Demo, RFQ and Quotation files, use their business delivery endpoints in the CRM API. Native File owner/share/list/detail/delete/private-URL and `File.get_content` reads are denied for the canonical File and same-URL aliases. `protect_service_managed_files.inventory` validates that every committed service File is private, canonical, attached to a live parent and has no independent same-URL alias. The migration stops before mutation when review is required; a clean run makes the technical owner Administrator and removes legacy File shares.

- Keep traffic and background writers paused from code rollout through migration and reconciliation. The provenance column must exist before new code serves requests. `add_file_content_hash_index` runs right after it and declares `File.content_hash` as indexed through a Property Setter, so a later File schema change (Custom Field, Customize Form, Frappe upgrade) keeps the `content_hash_index` that the runtime guards force. First run all four inventories on the release backup: `protect_contact_files.inventory`, `protect_visit_files.inventory`, `protect_controlled_document_files.inventory` and `protect_service_managed_files.inventory`. Public/remote Visit or Controlled Document files block migration because public URLs bypass Python, and so do Visit files whose Visit no longer exists (`missing-visit-parent`). Status, Demo, RFQ and Quotation files that are public, remote, noncanonical, detached from a live parent or shared with an independent same-URL alias block the last patch (`protect_service_managed_files`). Resolve their storage explicitly before continuing; these patches do not delete bytes. All noncanonical aliases of Contact, Visit, Controlled Document or service-managed blobs block their migration, folder rows included: review their independent grants and storage before rollout, without fabricating provenance or deleting unrelated files.
- Rehearse on the same database/files/config backup. Test both native File API and the saved private URL with A before/after transfer to B; repeat for soft deletion, role removal, invalid parent and deduplicated content. Verify B's allowed downloads as well as A's denial. Also test native insert, attach_file, reparenting, forged flags and setting `is_folder` against a Visit, followed by a normal scanned service upload.

These File guards do not intercept application code that opens a path returned by `File.get_full_path()` directly.

This change does not claim that historical Visit Files have been rescanned on production. That is a deployment check, not a property of a Git commit.
