## 5. 三条全生命周期流程

三条数据走的是同一条“成功成交并完成设备交付”的标准路径，但每次都创建全新的独立业务数据。这样用于验证流程可重复性、随机 ID、事务隔离和连续执行时是否会串数据。

### 5.1 Sales：客户与销售机会建立

每套流程执行并验证：

1. 创建半导体客户 Account。
2. 创建 Fab/Site。
3. 创建采购、良率工程和工艺整合联系人。
4. 创建 Qualified Lead。
5. 将 Lead 转换为已关联的 Account、Contact、Site 和 Opportunity。
6. 验证 Opportunity 初始阶段为“需求发现”，金额为 `CNY 4,860,000.00`。

结果：三套数据全部创建成功，Lead 转换后的主数据和 Opportunity 关联正确。

### 5.2 Sales 与 Manager：拜访闭环

每套流程执行并验证：

1. Sales 创建现场拜访。
2. 状态推进到 `Visited`。
3. 写入客户会议记录、参会人、议程、结论和下一步行动。
4. 状态推进到 `Minutes Submitted`。
5. 完成下一步行动。
6. Manager 完成审核，状态进入 `Manager Reviewed`。

结果：三套拜访状态、会议记录、负责人和 Manager 审核均正确留痕。

### 5.3 Sales：联系人文件

每套流程为采购联系人上传一份技术需求附件，并重新读取联系人文件列表验证文件 ID。

结果：附件写入和联系人关联均通过，测试结束后随隔离文件卷清理。

### 5.4 Sales、Engineer、Manager：Demo Request 审批

每套流程执行并验证：

1. Sales 创建并直接提交 Demo Request。
2. Demo Request 关联 Account、主要联系人和 Opportunity。
3. 填写晶圆尺寸、材料、检测指标、目标结果、测试设备、成功标准和 12 片 Wafer 数据。
4. Opportunity 自动推进到“Wafer Demo确认”。
5. Engineer 填写测试方案、设备、资源窗口、预计完成时间和技术风险后批准。
6. Manager 批准进入 Demo Test。
7. 系统创建唯一关联的 Evaluation/Demo Test。

结果：三套跨角色审批、状态、负责人、History Actor 和 Opportunity 联动均通过。

### 5.5 Engineer：Demo Test 执行

每套流程依次推进：

`Requested → Scope Confirmed → Sample Received → Scheduled → Testing → Internal Review → Customer Review → Accepted`

同时执行并验证：

- 上传 Internal Test Report。
- 上传 External Test Report。
- 新增完成状态的 Test Run。
- 写入 12 片 Wafer、Capture `96.8%`、False Positive `1.1%`、WPH `18.5`。
- 验证 Demo Workflow 中两份报告 ID 均存在。
- 验证 Test Run 指标可重新读取。
- Demo 接受后 Opportunity 自动推进到“预算审批”。

结果：三套 Demo Test 均成功 Accepted，报告、Test Run、Tracking History 和 Opportunity 联动一致。

### 5.6 Sales、Engineer、Manager：RFQ

每套标准流程执行并验证：

1. Sales 将 Opportunity 推进到“设备规格确认”。
2. Sales 创建 RFQ 并分配 Engineer。
3. Engineer 提交技术评审意见。
4. Manager 审核通过。
5. Opportunity 自动推进到“报价”。

RFQ 专项测试还覆盖：

- Sales、其他 Sales、当前 Engineer、其他 Engineer 的数据范围。
- Engineer 只能预览、未批准时不能下载。
- Manager 退回 RFQ。
- RFQ Revision 2 重新上传和再次审批。
- 批准后禁止重复审批和晚到修改。
- Manager 回退 Opportunity 后 RFQ 自动重开。
- 分配通知、退回通知、批准通知的收件人和路由。

结果：RFQ 标准流程和权限功能通过；TipRay 专项存在一项测试代码前置条件问题，详见第 8 节。

### 5.7 Sales 与 Manager：Quotation

每套流程执行并验证：

1. Sales 创建 Device Quotation。
2. 关联 Opportunity、联系人和 Site。
3. 写入设备行、数量、单价和四段付款比例。
4. Sales 提交审批。
5. Manager 批准商务条款和价格。
6. Sales 记录客户决定为 `Accepted`。
7. Opportunity 自动进入“采购流程”。
8. Sales 将 Opportunity 关闭为 `Won`，Forecast 为 `Closed`。

Quotation 专项 `14/14` 通过，另外覆盖：

- Account 360 中的客户报价。
- Sales 提交必须经过 Manager 审批。
- 保存草稿、版本历史、发布和 PDF。
- Device、Service、Others 报价。
- 付款比例总和门禁。
- 客户决定、过期处理和并发版本保护。
- 非整数设备数量拒绝。
- 发布失败时数据库和文件事务回滚。

结果：报价业务数据、审批、版本、客户决定和 Opportunity 联动均通过。

### 5.8 Sales：Booking

每套流程执行并验证：

1. 从 Won Opportunity 创建 Confirmed Equipment Booking。
2. 关联客户、联系人、Opportunity、设备、数量、DDL、币种和金额。
3. 验证 Booking 可在客户范围内重新查询。

Booking 专项 `6/6` 通过，另外覆盖：

- 来源、联系人状态和重复 Booking 规则。
- Owner、Account、Contact 数据范围。
- 锁定 Booking 不允许继续修改。
- 只有 Manager 可以删除 Booking。
- 通知创建失败时整体回滚。
- Service Booking 使用“服务完成”结束，不创建 Installed Tool。

结果：Equipment 和 Service 两种 Booking 分支均通过。

### 5.9 Sales 与 Engineer：Installed Tool

每套流程将 Confirmed Equipment Booking 转为 Installed Tool，并验证：

1. Site、Engineer、型号、位置、销售订单、合同、软件、固件和配置写入。
2. Serial Number 唯一性和系统生成/校验规则。
3. Booking 与 Installed Tool 形成双向业务关联。
4. Engineer 依次完成 `FAT → Shipment → Installation → SAT → Warranty`。
5. 每个生命周期节点记录完成日期、结果、问题、客户确认、备注和证据。
6. 完成后 `lifecycleCompleted=true`。
7. 新增软件版本记录，并将当前软件更新为新版本。
8. 新增质保服务记录，写入质保起止日期、服务合同和 PM 周期。

Installed Tool 专项 `14/14` 通过，另外覆盖：

- 旧里程碑迁移幂等性。
- 详情顺序和服务端权限。
- 转换事务原子性。
- Site、Engineer、Booking 状态校验。
- Serial Number 冲突和数据库竞态。
- 生命周期只能推进五步且完成后停止。
- 只有 Manager 或当前 Engineer 可以推进。
- CAS/版本冲突保护。
- History 与当前快照必须同时成功或同时回滚。
- 版本、服务、主档更新不能绕过审计命令。

结果：三台测试设备均完整进入 Warranty，版本、服务和审计记录一致。

## 8. 发现的问题

### 8.1 全新站点与旧受控文档测试基线不一致

严重程度：中，属于部署基线/测试契约问题。

现象：

- 全新隔离站点运行完整流程时，在读取 `DOC-ACONCA-FSBS-EDGE` 失败。
- 仓库存在 `install_approved_controlled_documents()`，但 `after_install()` 和 `after_migrate()` 没有调用它。
- 正式环境此前要求删除旧参考文档、从零维护文档库，因此“不自动恢复旧文档”可能是当前业务意图。
- 旧全流程测试仍把 Aconca 文档视为强制前置条件。

影响：

- 新站点无法直接通过旧全生命周期测试。
- 若未来部署要求自动带两份参考文档，安装流程不完整。
- 若未来部署明确不带参考文档，则旧测试应改用测试内创建的文档 Fixture，不能依赖生产参考文档。

建议：先确定产品规则，再选择一种修复方式：

1. 需要默认参考文档：在安装/迁移流程中幂等安装并增加安装契约测试。
2. 不需要默认参考文档：全流程测试自行创建并清理受控文档 Fixture。

### 8.2 RFQ TipRay 测试缺少 Opportunity 阶段准备

严重程度：低，测试代码问题。

现象：`test_tipray_file_can_be_created_and_downloaded_without_preview` 创建 Opportunity 后，没有将其推进到“设备规格确认”，随后直接创建 RFQ。

服务端按照业务规则返回：`RFQ can only be created when the Opportunity is in 设备规格确认.`

判断：服务端行为正确，测试前置条件错误。测试应先设置 Opportunity 阶段，再验证 TipRay 文件存储、禁止在线预览和原文件下载。

### 8.3 Quotation PDF CSS 警告

严重程度：低，观察项。

Quotation 测试中 PDF 渲染器报告 CSS Level 2.1 不支持 `display:grid` 和 `grid-template-columns`。所有 `14` 项测试仍通过，但本轮未逐页进行 PDF 视觉对比，因此复杂布局的最终排版仍建议纳入人工 UAT。

## 11. 最终评价

核心成功路径具备可重复性：三套独立数据均能从 Lead 一直推进到 Won、Booking、Installed Tool 和 Warranty，跨角色权限、状态联动、业务关联、通知和汇总数据整体可靠。

当前需要优先解决的不是主业务链回归，而是测试基线与产品规则的一致性：受控参考文档到底应由系统默认安装，还是应保持空库并由用户上传。确认该规则后，应同步修正安装钩子或全流程测试 Fixture。RFQ TipRay 用例只需补齐 Opportunity 阶段准备。
