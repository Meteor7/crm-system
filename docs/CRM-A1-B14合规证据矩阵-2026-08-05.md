## 6. A3/B14 最小实施影响面（历史设计记录，已实施）

### 6.1 A3 不需要重写 47 个组件

- 当前有 **47 个生产文件**直接导入 `@/demo/personnel`；其中绝大多数只调用 `personnelDisplayName`，少数调用 `PersonnelSelect`、`preferredPersonnelId` 或 mention 解析。
- 推荐在 `vite.config.ts` 中增加精确别名：Mock 构建仍指向现有 `src/demo/personnel.ts`；Frappe 构建将同一路径解析到新的服务器目录实现。别名必须位于通用 `@` 别名之前。
- Frappe 目录实现保持相同只读查询 API，但初始为空，并提供仅供 bootstrap 初始化的 replace 方法；目录使用 Vue reactive array，确保已挂载的 `PersonnelSelect` 会在 bootstrap 完成后更新。
- 因 `src/demo/identities.ts` 也通过该别名读取 `PERSONNEL`，Frappe 构建中的 `DEMO_IDENTITIES` 会自然为空，不需要重写 AppShell 的全部身份 UI；`usingMock` 继续控制 UI 是否显示。

### 6.2 Bootstrap 人员筛选规则

- `BootstrapDto` 新增 `personnel`，仅返回启用的 System User，且必须**恰好拥有一个** CRM Manager/Sales/Engineer 角色。
- 明确排除 `Guest`、`Administrator`、disabled user、Website User、无 CRM role 与多 CRM role 用户。
- 返回字段仅限 `id`（Frappe User.name）、display name、initials、公开 CRM role、team、`availableForAssignment=true`；不返回密码、API key、Token、session、手机号等敏感字段。
- 前端人员目录只负责显示和选项，不参与授权；服务端 `resolve_crm_role`、`assert_capability` 与 scope 仍是唯一权限权威。
- 空目录必须显示空选择器/未解析 ID，不得回退到 Alex 或任何静态人员。

### 6.3 B14 与同一 bootstrap 边界一起修复

- Frappe `loadBootstrap` 成功后调用 `listNotifications({page:1,pageSize:20})`，以服务器结果替换 Store；Mock 继续保留现有 Requirement seed 与本地 notifying proxy。
- Notification Store 新增 `replaceServerNotifications`，只把 `NotificationDto` 映射为 UI 数据；Frappe 初始 state 为空，不能先显示静态 seed。
- 打开通知时，Frappe 模式先调用 `markNotificationRead`，成功后再改本地状态；“全部已读”同理调用 `markAllNotificationsRead`。失败时保持未读并显示可重试错误，不能乐观吞错。
- 验收同时覆盖：空数据库无 Alex；两名真实 User 只看到自己的人员/通知；Frappe bundle 不含静态邮箱/名字/seed；Mock 回归不变；后端依旧拒绝伪造 owner。

## 7. A4/A5 收敛清单（历史设计记录，已实施）

### 7.1 A4 唯一 12-code 词表

| 最终 code | 旧码归并规则 |
|---|---|
| `UNAUTHENTICATED` | HTTP 401 / Guest / 失效会话；不能继续映射成 `PERMISSION_DENIED`。 |
| `PERMISSION_DENIED` | 角色/capability 不允许。 |
| `SCOPE_DENIED` | `SCOPE_DENIED`、`INSTALLED_TOOL_SCOPE_DENIED`、`INSTALLED_TOOL_REASSIGN_DENIED`。 |
| `NOT_FOUND` | 所有 `*_NOT_FOUND`。 |
| `VALIDATION_ERROR` | `INVALID_OWNER`、`BOOKING_SOURCE_REQUIRED`、`CONTACT_INACTIVE`、`LINK_MISMATCH`、`INVALID_REPORTING_LINE` 及普通字段校验。 |
| `CONFLICT` | `*_EXISTS`、`*_ALREADY_*`、`*_LOCKED`、`DUPLICATE_*`、CONTACT/SITE account mismatch、merge conflict、`RUN_EXISTS`。 |
| `INVALID_TRANSITION` | `INVALID_REPORT_STAGE`、`INVALID_RUN_STAGE`、`BOOKING_NOT_CONFIRMED`、`BOOKING_SOURCE_INVALID`、`BOOKING_STATUS_INVALID`。 |
| `VERSION_CONFLICT` | canonical modified 不一致。 |
| `REPORT_NOT_READY` | `REPORT_NOT_READY`、`EVALUATION_EXISTS`。 |
| `BACKEND_NOT_CONNECTED` | Mock/Frappe adapter 边界未连接。 |
| `NETWORK_ERROR` | fetch/timeout/abort；原 `UPSTREAM_TIMEOUT` 合并到此，`retryable=true`。 |
| `INTERNAL_ERROR` | 未知/5xx，`retryable=true`，不向客户端泄露 traceback。 |

实施时需要同时修改后端异常产出、Frappe adapter、Mock adapter、`mapRequestError` 与所有断言；只在 adapter 做映射而保留后端旧码会让服务端契约测试继续漂移，不算完成。

### 7.2 A5 capability 分类

| 分类 | capability | 结论 |
|---|---|---|
| 后端直接强制 | `dashboard:view`、`account:*`、`contact:*`、`stakeholder:*`、`deal:*`、`visit:*`、`demo_request:view/create`、`demo_report:*`、`evaluation:*`、`installed_tool:write`、`service:view` | 保留；补充逐 endpoint 矩阵测试。 |
| 后端动态强制 | `demo_request:engineering_review`、`demo_request:manager_approve` | 保留；状态机按 command 选择 capability。 |
| 仅 UI/兼容 | `account_report:export`、`dashboard:management` | 删除或改由已有 read capability 控制；不能声称是服务端权限。 |
| 只读视图未强制 | `requirement:view`、`contract:view` | 目前只检查“是 CRM 用户”；必须改成服务端 `assert_capability`，或从词表删除并统一使用 `account:view`。 |
| 无生产端点 | `requirement:write`、`service:write`、`procedure:view`、`procedure:execute`、`system:configure` | 推荐删除，避免死权限；不为保留词表而新增空壳功能。 |

最终原则：capability 只有在至少一个服务端 endpoint/command 强制它且有拒绝测试时才允许存在；导航或按钮使用不构成安全证据。
