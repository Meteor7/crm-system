# CRM Mock Demo P1 通知问题后续解决方案

## 文档范围

本文只记录 2026-08-03 对抗性审查中除 P0 之外的 P1 问题，不代表当前 Mock Demo 已具备正式后端能力。

当前项目以 Vue 前端和 Mock 数据为主。以下方案应在接入认证、业务后端和数据库时实施；在此之前，只对影响演示正确性的前端跳转问题做必要修正。

## P1-1 通知刷新后丢失

### 当前问题

- 负责人变更和 Comment `@` 通知只保存在 Pinia 内存中。
- 页面刷新或重新打开系统后，通知消失，但 Comment 等业务数据仍然存在。
- 当前通知写入与业务写入不是同一个事务，可能出现“业务成功但没有通知”。

### 后端方案

1. 建立通知表，至少保存：通知 ID、收件人用户 ID、业务类型、业务记录 ID、标题、摘要、创建时间、已读时间。
2. 负责人变更、Comment `@` 与对应业务写入在同一事务内创建通知，或通过可靠的事务事件表异步创建。
3. 消息中心按登录用户分页查询通知，已读状态由后端持久化。
4. 前端身份切换、登录和页面刷新后重新请求当前用户的通知，不复用上一身份的内存队列。

### 验收标准

- 刷新页面后，通知仍存在且已读状态保持一致。
- 业务写入失败时不产生通知；业务写入成功后通知不会永久缺失。
- 用户只能查询和修改自己的通知状态。

## P1-2 通知链接不能准确定位业务记录

### 当前问题

- Demo Test 状态通知使用 Evaluation ID 打开按 Demo Request ID 查询的详情页。
- Visit 和 Installed Tool 通知使用 `highlight` 参数，但对应页面未消费该参数。
- Evaluation 页面读取 `focus`，通知链接却传递 `highlight`。

### 解决方案

1. 后端通知不要拼接易漂移的完整 URL，返回统一的 `resourceType`、`resourceId` 和必要的父记录 ID。
2. 前端建立唯一的通知跳转映射，将业务资源转换为当前路由。
3. Demo Test 通知同时返回 Evaluation ID 和 Demo Request ID，详情页使用 Demo Request ID，页面内部再定位 Evaluation。
4. Visit、Installed Tool 和 Evaluation 页面统一使用同一个定位参数，并在进入页面后选中或高亮目标记录。

### 验收标准

- 每类通知点击后都能打开正确页面并直接定位唯一目标记录。
- 目标记录不存在或无权访问时显示明确提示，不回退到列表第一条记录。
- 路由参数名称由集中映射维护，不在各通知写入点单独拼接。

## P1-3 无收件人通知被所有身份看到

### 当前问题

Test Run、DDL、报告配置和报告发布等通知未设置收件人。当前前端把无收件人通知视为全员通知，因此不同角色都可能看到不属于自己的业务进度。

### 后端方案

1. 普通业务通知必须保存明确的 `recipientUserId`，禁止用空收件人表达默认广播。
2. 一项业务需要通知多人时，使用通知收件人关联表，或为每位收件人创建独立通知记录。
3. 真正的系统广播必须使用显式的 `audienceType`，并在后端进行角色、组织或团队范围校验。
4. 通知查询必须以当前认证用户为边界，前端筛选只作为显示逻辑，不能作为权限控制。

### 验收标准

- Test Run、DDL 和报告通知只对项目相关人员可见。
- 空收件人数据不能进入普通通知表，或在写入时被拒绝。
- 用户修改已读状态不会影响其他收件人的独立已读状态。

## 推荐实施顺序

1. 先确定通知数据模型、收件人模型和权限查询规则。
2. 实现通知持久化与按当前用户查询。
3. 将 Comment `@`、负责人变更和 Demo Test 事件接入后端通知事务。
4. 统一前端通知跳转映射并补齐目标定位。
5. 增加跨身份、刷新恢复、无权访问和目标不存在的端到端测试。

## Mock 与正式环境边界

Mock Demo 可以验证页面交互、人员选择和消息中心展示，但不能证明正式环境中的身份认证、数据隔离、事务一致性和通知可靠投递。上述能力必须以正式后端接口、数据库约束和权限测试结果为验收依据。
