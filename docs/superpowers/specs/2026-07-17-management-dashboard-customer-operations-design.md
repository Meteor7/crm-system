# 经营决策中心与客户经营能力设计

**日期：** 2026-07-17
**状态：** 需求已确认，待实施
**范围：** 经营决策中心、客户档案与客户报告、拜访管理、关键人与组织关系、Demo/Wafer Test 卡片对齐

## 1. 目标与约束

本轮在现有半导体 CRM MVP 上完成一组面向管理者和客户经营场景的快速迭代：

1. 将现有首页改名为“经营决策中心”，在管理者权限下集中展示能够由现有明细真实计算的经营数据。
2. 将客户档案恢复为原型的左侧客户列表、右侧完整档案结构。
3. 按原型样例导出五工作表客户 360 Excel 报告。
4. 落地拜访管理和关键人与组织关系页面，并回写客户档案和客户报告。
5. 统一 Demo/Wafer Test 案例卡片尺寸和内容区位置。

约束：

- 不为经营决策中心补造线索、配额、服务工单等不存在的业务数据。
- 不再使用固定趋势数组或按比例缩放金额来模拟月度、季度数据。
- 缺少且不能确定性推导的客户报告字段统一显示“—”。
- 继续使用 Mock Adapter 的内存状态，不引入 localStorage。
- 为快速迭代，只执行与本轮改动直接相关的定向测试、类型检查、构建检查和关键页面浏览器验收，不执行完整全量回归。

## 2. 权限和入口

- 用户界面中的权限名称统一为“管理者权限”。经营决策中心沿用现有首页和导航入口，不新增“驾驶舱”页面。
- 新增 `dashboard:management` capability 作为完整管理看板的权限判断。管理者权限严格只读，不包含 Demo 审批、工程评估、Test Run、拜访审核或客户资料修改。
- 具备管理者权限的用户看到跨团队经营决策中心；不具备该权限的用户保留业务执行首页。
- 本轮角色和数据范围如下：

| 角色 | 数据范围 | 允许操作 |
| --- | --- | --- |
| CRM Administrator | 全部客户、全部团队 | 全部 CRM 业务读写、角色/字典/权限配置；不自动获得服务器管理权限 |
| Management Viewer（管理者权限） | 跨团队全局数据 | 只读经营决策中心和全部业务摘要，可导出全部客户报告，不执行任何审批或写操作 |
| Sales Manager | 自己负责的团队 | 维护团队客户和销售数据、审核拜访、经理审批 Demo、查看团队报表和客户报告 |
| Sales User | 自己负责的客户 | 维护客户、关键人、需求、商机和拜访，创建/修改/提交自己的 Demo Request，查看相关验证、合同和客户报告 |
| FAE / Applied Engineer | 被分配的 Demo 和关联客户 | 工程评估、退回 Demo、维护 Evaluation/Wafer Test/Test Run；不能修改商业金额、Booking、合同或客户关系 |

- 原架构中的 Intelligence Analyst 随客户情报模块撤下，本轮不保留。
- `capabilities` 只用于界面体验控制；生产环境最终权限必须由 Frappe Role、User Permission、DocType 权限和写接口再次裁决。
- 本地 Mock 也必须执行 capability 和数据范围校验，不能仅隐藏按钮。
- 拜访和关键人分别使用 `visit:view`、`visit:write`、`stakeholder:view`、`stakeholder:write`；拜访管理者审核使用独立 `visit:review`。
- Demo 使用 `demo_request:create`、`demo_request:engineering_review`、`demo_request:manager_approve`；Evaluation 使用 `evaluation:view`、`evaluation:write`；客户报告使用 `account_report:export`。

## 3. 经营决策中心

### 3.1 数据事实来源

经营决策中心以业务明细为事实来源：

- 商机金额、阶段、概率、负责人：`OpportunityDto[]`
- Booking 金额、状态、日期、负责人：`BookingDto[]`
- 客户等级、地区、业务领域、风险、完整度：`AccountSummaryDto[]`
- 采购需求：`RequirementDto[]`
- 行动项：`ActionDto[]`
- Demo Request、Evaluation/Test Run、合同：各自明细集合
- 拜访：本轮新增的 `VisitDto[]`

`AccountSummaryDto.pipelineAmount` 仅为列表摘要，不作为管理指标事实来源；当前它与商机明细合计不一致。所有管理指标统一从商机明细重新汇总。

### 3.2 核心口径

- 当前开放 Pipeline：所有非 `Won`、非 `Lost` 商机金额之和。
- 加权 Pipeline：开放商机 `amount × probability / 100` 之和。
- Confirmed Booking：`status === 'Confirmed'` 的 Booking 金额之和。
- 累计 Closed Won：`stage === 'Won'` 的商机金额之和。因为当前没有成交日期，不标注为“本季度 Closed Won”。
- Booking 月度分布：按真实 `bookingDate` 聚合；没有数据的月份不补值。
- 负责人排行：分别按当前 Pipeline、加权 Pipeline 和 Confirmed Booking 汇总。
- Top 客户：分别按当前 Pipeline 和 Confirmed Booking 汇总；客户不足 10 个时显示“Top 客户”，不误标为 Top 10。

现有明细的基准值为：开放 Pipeline ¥9,710 万、加权 Pipeline 约 ¥6,921.9 万、Confirmed Booking ¥2,240 万、累计 Closed Won ¥1,880 万。实现测试应保护这些口径。

### 3.3 页面分区

管理者首页采用从结果到过程的纵向分区：

1. **核心指标：** 开放 Pipeline、加权 Pipeline、Confirmed Booking、累计 Closed Won。
2. **管线分析：** 阶段漏斗、各阶段金额与加权金额、负责人排行。
3. **客户贡献：** Top 客户、业务领域、地区、客户等级、风险等级、档案完整度。
4. **经营流程：** 采购需求状态与预算状态、行动项和逾期分布、Demo Request 状态与优先级、Evaluation/Wafer Test 状态与运行结果、合同类型/状态/金额/到期风险、拜访状态与负责人。

每个图表显示统计口径或数据来源说明。页面保留更新时间和 stale 提示。当前数据不支持统一的月/季/年筛选，因此不对当前快照指标提供伪时间筛选；只有 Booking 图表使用真实日期。

### 3.4 明确不展示的内容

在没有对应明细前，不展示：季度目标完成率、同比/环比成交趋势、Forecast Category、预计成交日期分布、线索来源、线索转化、失单原因、可靠的 Win Rate、电话/邮件/会议活动量、客户规模营收、服务工单和 CSAT。

## 4. 客户档案

### 4.1 页面结构

- 桌面端：左侧客户列表，右侧常驻客户详情。
- 小屏：客户列表和详情上下排列。
- 默认选中第一个筛选结果；切换客户不丢失列表上下文。
- 右侧顶部展示客户等级、负责人、地区、业务领域、Pipeline、购买意愿和档案完整度。
- 详情按经营摘要、Site、关键人、需求、商机、Demo/Wafer Test、合同、拜访和下一步行动组织。
- 当前表格加抽屉的 Account 360 交互被替换，但已有字段和状态组件尽量复用。

### 4.2 数据一致性

- 关键人数以关键人明细集合为准，不使用与明细不一致的摘要数量。
- 客户 Pipeline 详情以商机明细聚合为准。
- 没有明细的客户显示明确空状态，不根据摘要数量生成虚构记录。

## 5. 客户 360 Excel 报告

### 5.1 输出结构

导出参考 `CUSTOMER06_演示_Customer_360_2026-07-17.xlsx` 的视觉样式和原型生成逻辑，保持五个工作表：

1. `客户全貌 Overview`
2. `商机 Opportunities`
3. `需求与行动 Actions`
4. `关键人与拜访 People`
5. `Demo与合同 Demo`

保留中英文标题、标题带、合理列宽、冻结标题行、金额/日期/百分比数字格式和各区块的层级样式。文件名为 `<客户简称>_Customer_360_<YYYY-MM-DD>.xlsx`。

### 5.2 数据规则

- 报告始终导出当前选中客户的数据，不复制样例中的 CUSTOMER06 演示数值。
- 当前示例企业015没有 Booking 时，Confirmed Booking 显示 0。
- 数量以实际明细为准，例如需求和关键人数不套用样例数量。
- `probability`、Capture、FP 在写入 Excel 时换算为 Excel 百分比数值并应用百分比格式。
- 完成 Runs、平均 Capture、平均 FP 等只做确定性聚合。
- 综合行动队列可从 Action、Requirement、Opportunity、Demo Request、Visit 的下一步行动合并，并按客户、标题、负责人和截止日期去重。
- 缺失的英文行动、付款节点、付款账期、PO/Shipment/FAT 日期、需求优先级/预计采购日期/决策人等显示“—”，不自动翻译或伪造。
- 风险只使用明确记录或透明规则，例如退回的 Demo Request、逾期行动、未签署/到期合同；规则生成项要保留来源记录 ID。

### 5.3 实现方式

将原型中的无依赖 XLSX ZIP/XML 生成逻辑抽离为独立模块，报告数据组织与二进制生成分开：

- `customer-report-model.ts`：构建五页工作簿模型，便于测试字段和口径。
- `xlsx-writer.ts`：生成 Excel 文件并触发浏览器下载。
- 不新增体积较大的前端表格依赖。
- 完成后使用独立表格检查工具重新导入下载文件，确认五个工作表、关键单元格和视觉渲染。

## 6. 拜访管理

### 6.1 数据模型

`VisitDto` 包含：ID、客户、业务领域、主题、日期、方式、状态、负责人、目标、结果、下一步行动、行动负责人、截止日期、行动完成状态。

状态流：

`Planned` → `Visited` → `Minutes Submitted` → `Manager Reviewed`

用户界面标签：待拜访 → 已拜访 → 已提交纪要 → 管理者已审核。

### 6.2 页面和操作

- 导航增加“拜访管理”。
- 支持日期范围、客户、状态、负责人筛选。
- 卡片或列表显示状态流、目标、结果、下一步行动、责任人和截止日期。
- 支持新建拜访、推进状态、提交纪要和完成后续行动。
- 管理者审核只对管理者权限开放。
- 拜访自动进入对应客户 Account 360 和 Excel 报告。

## 7. 关键人与组织关系

### 7.1 数据模型

扩展 `ContactDto`：采购角色扩展为 Decision Maker、Economic Buyer、Champion、Technical Evaluator、Procurement、Influencer、Blocker、User，并增加 `reportsTo`、`email`。

现有记录没有 `reportsTo` 或邮箱时显示“未设置”或“—”，不为现有人员推断汇报关系。

### 7.2 页面和操作

- 导航增加“关键人与组织关系”。
- 左侧客户选择，右侧组织关系图和关键人明细表。
- 组织树由 `reportsTo` 生成；没有汇报关系的人员作为根节点展示。
- 支持新增和编辑关键人。
- 禁止自我汇报和循环汇报。
- 对缺少 Decision Maker 或 Economic Buyer 的客户给出资料缺口提示。
- 关键人变更同步反映到客户档案和客户报告。

## 8. Demo/Wafer Test 卡片对齐

当前页面没有案例图片，本需求按案例卡片尺寸对齐实现：

- 看板列宽一致，案例卡片使用统一高度。
- 卡片采用固定内容区：状态/客户、标题、Wafer 或挂起原因、来源、Test Runs、操作区、日期页脚。
- 标题和普通说明限制显示行数。
- Test Runs 区域固定高度，超出时内部滚动。
- 操作区和页脚固定在卡片底部，避免不同内容量造成按钮错位。

## 9. API 和状态策略

- 在 `CrmApi` 中增加拜访列表/创建/更新和关键人列表/创建/更新方法。
- Mock Adapter 使用模块内可变副本，沿用现有响应延迟、requestId、错误结构和 capability 检查。
- `getAccount360` 增加 visits，并使用关键人明细计算展示数量。
- Frappe Adapter 保持与接口同形；没有后端端点时返回明确的未接入错误，不静默伪成功。

## 10. 错误和空状态

- Dashboard 任一明细集合为空时，对应图表显示空状态，不自动补零生成趋势。
- 客户报告导出失败时显示可操作错误，不产生损坏文件。
- 拜访和关键人操作沿用 loading、denied、error、empty、stale 状态组件。
- 组织关系存在无效父节点时，将该人员显示为根节点并给出数据质量提示；循环关系在保存前阻止。

## 11. 定向验证策略

本轮不运行完整全量测试，定向验证如下：

1. Dashboard 聚合函数：四个基准金额、漏斗、负责人/客户/地区/业务领域聚合，以及无数据空状态。
2. 管理者权限：有权限显示经营决策中心，无权限保留执行首页；拜访审核权限受控。
3. 客户档案：列表切换、详情同步、明细数量口径。
4. 报告模型与导出：五个工作表、当前客户隔离、缺失值“—”、金额/百分比类型和下载文件名。
5. 拜访：筛选、创建、状态推进、纪要、行动完成和 Account 360 关联。
6. 关键人：新增/编辑、组织树、自我/循环汇报保护和客户关联。
7. Evaluation 卡片：统一尺寸、长标题和多 Runs 的布局。
8. 运行相关定向 Vitest 文件、`vue-tsc --noEmit`、生产构建，以及这些页面的浏览器验收。

## 12. 完成标准

- “经营决策中心”只展示现有明细能够支撑的指标，所有金额可以回溯到记录。
- 首页无固定趋势数组和比例缩放金额。
- 客户档案符合原型分栏逻辑。
- 导出的 Excel 与样例保持相同五页结构和视觉语言，且内容来自选中客户。
- 拜访、组织关系可用并进入客户档案和报告。
- Demo/Wafer Test 案例卡片对齐。
- 本轮定向测试、类型检查和构建通过。
