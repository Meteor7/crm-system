## 3 十二个 PR 的实施与验收

以下源码路径均相对仓库根目录。后端简称 `app/` 指 `backend/apps/rayher_crm/rayher_crm/`。新文件名是建议，开工时结合最新代码确定。

### PR01 地域维护与销售归属

**难度 3/5；关联 #17；前置：地域和人员名单。**

复用现有 `CRM Sales Territory`、`services/territories.py` 和 `territory_tree.py`，增加经理维护入口、节点层级校验、自定义区域挂接及销售归属。销售归属带生效日期，保留变更记录。v1 每个末级区域在同一时段只有一个负责人，一名销售是否可负责多个区域按业务名单确定。地域用于分类和汇总，继续沿用现有数据访问规则。

已有客户区域字符串和树节点名称是兼容约束。第一版优先采用停用和调整父节点，暂不开放任意改名；迁移提供原值、目标节点、无法映射值清单，不猜客户归属。

主要改动：现有地域服务和 DocType、建议新增归属记录与 `api/v1/territories.py`、经理维护页面、现有 `RegionSelect.vue`；新增对象接入现有权限登记。

验收：

- 父节点选中全部后代；节点不能成为自己的后代，非法层级被拒绝。
- 同一区域的归属时间不能冲突；未分配显示未分配。
- 自定义区域挂接后可筛选，未映射客户仍可在全部范围找到。
- 调整和停用不删除已有业务记录，重复迁移结果一致。

### PR02 团队和地域目标汇总

**难度 4/5；关联 #17、#20；依赖 PR01。**

扩展 `CRM Cockpit Target` 和 `services/cockpit.py:attach_targets`，支持个人周 KPI、团队周目标及地域年度订单目标，将其接入目标线、达成率与管线覆盖倍数。个人目标的原接口和数据保持可读。

建议年度订单目标只在末级地域维护，父级自动求和；禁止再把父级金额叠加一次。缺少某个子地域目标时显示不完整，不能把已填部分显示成完整总目标。团队范围及“个人目标之和”和“独立团队目标”的选择须先确认，同一指标不能同时叠加两种来源。设备或市场未分配目标时仍显示不适用，不按数量平均分摊。

主要改动：目标 DocType、`cockpit.py`、`cockpit_conversion.py`、Review 目标编辑和展示；目标读接口预留给 PR08。

验收：

- 选中国时各地区订单和目标只计一次；个人/团队切换不混用分母。
- 目标为零、未设置、部分缺失分别显示；已达年度目标时覆盖倍数不除以零。
- 周/月/季/年边界及闰年目标线正确；不擅自把一个周目标乘成其他期间目标。
- 目标修改有版本冲突检查和历史记录，明细可解释汇总来源。

### PR03 活动分类与业务时间

**难度 5/5；关联 #26、#19；最先实施的关键任务。**

建立供 Review、Plan 和查询复用的活动读取合同，优先适配现有拜访、Lead 转化、Test Run、报价及商机行动，不要求销售把同一业务再录入一次。没有现有来源的跟进和 Event 由 PR07 增加业务入口。

建议活动投影包含来源类型、来源 ID、事件 ID、关联客户/商机、销售、类别、计划日期、实际发生或完成时间、记录时间、状态及证据来源。业务事实按实际时间归期；无法证实的旧完成时间保持未知。去重使用来源身份与有效事件，不能按标题或客户名猜测。

新老客分类已由用户确认：客户主档维护“潜在客户／老客户／未分类”，拜访首次离开 Planned 时保存当时分类和捕获时间。后续客户分类修改不改变拜访快照；历史无证据的拜访保留未分类。拜访的业务归期仍使用 visit_date，快照时间只是实际录入完成的时间，不倒推为拜访当天的客户关系。现有合同中的拜访完成状态、Demo 按完成 Test Run 计数、报价首次发布计数先保持。已完成行动只依据审计中的真实完成转换补时间，找不到证据时保持未知；更改备注不算一次新活动，完成后重开清除旧完成时间，再次完成形成当前完成周期。

主要改动：建议新增 `services/activities.py`，适配 `visits.py`、`evaluations.py`、`quotations.py`、`opportunities.py`，必要的 Action 字段/迁移，以及 `cockpit_metrics.py`、`cockpit_plan.py` 的共用读取入口。保持旧 API 可用，避免一次重写全部工作流。

验收：

- 同一拜访从客户和商机两个入口出现，计数仍为一。
- 完成、取消、重开、改期和补录不重复计；跨周按业务时间归属。
- 报价改版、Demo 复测严格遵循选定合同，并用实例证明。
- 有一条未知完成时间时，结果说明缺失，不冒充全量精确值。
- 统一定义最后实质活动时间，Review 停滞和 PR09 查询使用同一结果。

### PR06 Demo 设备不可用提醒

主要改动：Demo 安排字段、建议新增资源不可用记录及维护入口、相关服务与 Warnings；接入现有通知和权限登记。

验收：

- 同平台不同设备不误报；相邻但不重叠的时段按确认的边界规则处理。
- 已取消、已终止、已完成 Demo 不进入未来不可用提醒。

### PR10 查询分享与完整导出

**难度 4/5；关联 #21、#86；依赖 PR09。**

保存查询支持指定用户只读分享、撤销、另存个人副本；原定义仅作者或已明确授权角色修改。分享的是查询定义，接收人每次查询和导出仍使用自己的当前数据范围。

导出补查询名、分组工作表名、冻结表头、当前选列和人民币百万元数值。未知金额保留空值并说明缺失数量，不能变成零。

本项从上轮粗估的 3/5 调整为 4/5：当前 `export.ts` 分页比较摘要并不足以证明所有行来自同一集合。因此本 PR 必须完成本功能所需的一致导出方案，例如在服务端一次一致读取生成当前范围的结果；如选择分页快照，需写清有效期和权限变化处理。不能仅改文件名便关闭“完整导出”验收。只解决该导出路径，不扩建通用快照平台。

主要改动：保存查询 DocType/服务/API、分享界面、`export.ts` 和导出服务；新增字段进入现有权限登记与安装检查。

验收：

### PR11 商机资料与评分卡入口

**难度 2/5；关联 #29；可独立实施。**

建议以商机固定资料页作为逻辑共享目录，自动聚合已有 Status 附件、Demo 报告、RFQ、报价及可关联的拜访记录，不复制文件。增加 Product/Deal scorecard 链接、Blue Sheet 直达和缺失提示。

原 SPEC 写的是自动创建共享文件夹；采用 CRM 内聚合页是本次建议的实现方式，需要业务认可其等价性。如要求外部存储中的物理文件夹，本 PR 不能据此宣称已满足，应调整范围。评分卡只做链接，不开发评分引擎。

主要改动：建议新增 `services/opportunity_documents.py`，商机只读 API、链接字段、`OpportunityDetailPage.vue` 和资料组件；使用已有文件服务获取资料，保留其访问控制。

验收：

- 新商机自动有稳定资料入口，重复打开不创建重复文件或目录。
- 商机范围内但当前用户无权访问的资料不显示；受控文档仍走原流程。
- 链接缺失、错误或资料删除后的提示明确；合法链接可打开。
- 商机资料和 Blue Sheet 可相互返回，不要求在两个页面重复上传。

### PR12 Blue Sheet 自动联动

**难度 4/5；关联 #29、#27；依赖 PR03、PR04、PR05、PR07。**

在现有红旗上补稳定标识、严重程度和处理状态，进入 Warnings；复用已有行动进入 Plan 的能力。根据已确认的关键人覆盖、态度和红旗规则生成概率建议，展示依据和规则版本，由销售确认后走现有概率更新接口；降档仍需原因和补救计划。

竞争信息作为复盘时的可引用证据和分类辅助，不能自动写成已确认丢单原因。既有 Single Sales Objective、response mode、Win Result 和竞争明细继续复用。

主要改动：商机红旗结构的兼容迁移、建议规则服务、商机详情、Warnings、复盘入口；建议结果不增加概率百分比。

验收：

- 同一红旗只产生一个有效提醒，修改严重程度、解决或删除后的状态同步。
- 旧字符串红旗完整保留；没有依据时不擅自补高严重程度。
- 同样输入得到同样建议及理由；未确认不改变销售设置。
- 销售确认建议时重新检查版本，不能用旧建议覆盖已变化的商机；降档审计仍完整。
- 行动完成后 Plan 和预警同步，竞争记录引用不会冒充已完成复盘。

## 5 验证与集成方式

每个 PR 开始时重新核对 main 和对应 issue，确认依赖已包含。建议分支采用 `codex/philippe-01-territory-admin` 等编号名称；先查找可复用工作区，避免覆盖他人工作。当前旧 checkout 不执行强制同步。

按照最新主干的 `AGENTS.md`，真实运行环境为 Frappe。新功能通过真实后端以及前端 API stub/HTTP fake 测试；`mock-adapter.ts` 只在类型合同要求时增加抛错桩，不实现另一套业务流程。

每项实现应留下以下证据：

1. 范围与数据合同：明确新增、复用、保留的规则和需要的数据迁移。
2. 针对性测试：优先覆盖时间、去重、未知值、范围、并发修改和旧数据兼容等实际风险，不为简单文案另建镜像测试。
3. 前端检查：`pnpm typecheck`、相关 Vitest 用例和构建；最终候选执行完整门禁。
4. 后端改动通过干净工作区的 `pwsh -NoProfile -File backend/tests/run-release-gate.ps1 -StartBackend` 验证。脚本构建镜像，不能用旧容器测试磁盘上的新代码；本地脚本固定测试项目名，相关运行串行，避免共用容器互相干扰。
5. GitHub `release-gate` 针对最终提交通过，核对后端、前端及打包结果；记录实际审查结论和修复，不把计划检查写成通过。实施时沿用已有项目审查约定，不因拆 PR 而省略。
6. 在真实后端上查看新增界面，至少核对英文主要流程、正常和缺数据状态，并确认受影响角色的入口。涉及跨页联动的 PR 验证最终组合，不能只引用各分支单独通过的结果。

新 DocType、API、附件链接和分享功能直接接入已合入的权限登记、文件和通知服务。相关回归属于新功能自身的完整性，不额外开一轮通用权限重构。

每批验收至少准备：新客和老客、两个地域、两位销售、两种设备、已知和未知金额、跨周/跨季度日期、待复盘和已复盘丢单、完成后重开的行动。测试数据留在隔离站点。以一组可人工核对的预期值检查卡片、明细和导出。

## 6 发布与完成判定

最终完成不仅看 PR 是否合并。每批交付先固定提交与构建产物，使用该候选运行迁移和恢复演练，再由销售经理按实际周会顺序完成 Review → Warnings → Plan → Opportunities 验收。

业务数据准备包括真实目标、销售地域归属、必要的存量概率档位、设备资料和有证据的历史覆盖起点。代码具备能力但数据未准备时，分别记录“已实现”和“待业务启用”。本次未重新检查生产环境，不能把主干版本当成生产版本。

发布前备份数据库、公共/私有附件及配置；需要恢复时遵循现有“备份还原加匹配镜像”流程。生产日期、停写窗口和执行安排在候选通过验收后落实，本计划不启动部署。

交付完成须同时满足：

- 12 项承诺功能均有代码、最终提交上的检查和业务验收证据。
- 统计与查询采用已确认的口径；待定资料、正式规则和配置没有用假值填补。
- Review、Warnings、Plan、导出及 Blue Sheet 使用同一业务事实，未破坏已有七阶段、金额和 Demo 流程。
- 影响本次使用的缺陷已处理，未覆盖的事项明确归属；只关闭验收范围确已完成的 issue。
