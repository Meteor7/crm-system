# CRM 登录态失效回登录页最小改动实现规范

日期：2026-08-28
适用范围：Frappe CRM 前端真实运行时
目标：登录态失效时回到登录页，不改变正常权限控制。

## 1. 问题定义

当用户直接打开 CRM 资源地址，或已登录用户的 `sid` 过期后刷新页面，bootstrap 请求可能返回 403。前端若只把 401 识别为未认证，就会停留在空 CRM 壳中，用户无法重新登录。

## 2. 目标行为

以下场景必须跳转到 Frappe 登录页：

- Guest 直接访问 `/crm`；
- 登录态失效后刷新 CRM 页面；
- 生成的静态资源地址被旧 `sid` 访问；
- bootstrap 明确返回未认证结果。

跳转必须保留原访问地址，登录成功后可以返回原页面。例如：

```text
/login?redirect-to=%2Fassets%2Frayher_crm%2Fcrm%2Findex.html%3Fv%3D...%23%2Fdashboard
```

## 3. 最小改动边界

只允许修改以下两类位置：

1. bootstrap 接口的统一错误归一化；
2. 前端 `loadBootstrap()` 对“未认证 bootstrap 失败”的登录跳转处理。

不得顺手修改：

- 业务模块权限查询；
- Sales、Manager、Engineer 角色能力；
- Mock 身份切换逻辑；
- 数据库用户、角色或业务数据；
- 所有 403 的统一含义。

## 4. 认证与权限判定规则

| 场景 | HTTP | 前端错误码 | 页面行为 |
| --- | ---: | --- | --- |
| Guest/过期 sid，bootstrap 判定未认证 | 401，或可明确识别为未认证的 403 | `UNAUTHENTICATED` | 跳转登录页 |
| 已登录但没有模块权限 | 403 | `PERMISSION_DENIED` | 保留无权限提示，不跳登录 |
| 后端暂时异常 | 5xx | `INTERNAL_ERROR` | 保留错误提示，可重试 |
| 网络超时/断开 | 无响应 | `NETWORK_ERROR` | 保留网络错误提示，可重试 |

核心要求：不能把所有 403 都直接改成登录跳转。

## 5. 推荐实现顺序

1. 确认 bootstrap 使用项目统一的 API 错误封装；
2. 确认 Frappe 未登录会话返回 `UNAUTHENTICATED` 或标准 401；
3. 在前端 bootstrap 失败分支中，仅对 `UNAUTHENTICATED` 执行登录跳转；
4. 使用当前 `pathname + search + hash` 生成 `redirect-to`，并进行 URL 编码；
5. 跳转前不要清理业务数据、切换 Mock 身份或重置 Pinia 以外的服务器状态；
6. 增加回归测试，覆盖登录跳转和真实权限错误不跳转两条路径。

## 6. 验收用例

### 用例 A：Guest 访问

1. 用无 Cookie 浏览器打开 `/crm`。
2. 预期收到 Frappe 登录页跳转，不加载 CRM 空壳。

### 用例 B：sid 过期

1. 登录 CRM 并打开 Dashboard。
2. 删除浏览器 `sid`，或使会话过期。
3. 刷新当前资源地址。
4. 预期跳转 `/login?redirect-to=...`，且 `redirect-to` 保留原 hash 路由。

### 用例 C：有效用户无权限

1. 使用有效 Engineer 或 Sales 会话访问禁止模块。
2. 预期显示标准无权限提示。
3. 不得跳转登录页。

### 用例 D：后端异常

1. 让 bootstrap 返回 500 或制造网络超时。
2. 预期显示服务不可用/网络错误。
3. 不得伪装成未登录。

## 7. 必须执行的验证

- `npm.cmd run typecheck`；
- `npx.cmd vitest run src/stores/app.test.ts src/api/frappe-adapter.test.ts`；
- 真实 Frappe 会话下完成 Guest、过期 sid、有效无权限三类浏览器验证；
- staging 验证通过后，记录 HTTP 状态、最终 URL 和浏览器身份，不记录 Cookie、Token 或密码。

## 8. 发布要求

- 该改动必须单独 commit，提交说明包含“unauthenticated bootstrap redirect”；
- 不修改 staging 数据库内容；
- 不删除用户或强制注销全部会话；
- Product 发布前仍需验证禁用/删除测试账号后的旧会话行为；
- 若后端只能返回无法区分的 403，先修复错误分类，再修改前端，不得用“全部 403 跳登录”绕过权限语义。

## 9. 完成标准

只有同时满足以下条件，才可将问题标记为已修复：

1. Guest 和过期 sid 均稳定回到登录页；
2. `redirect-to` 保留原页面路径和 hash；
3. 有效用户的 403 权限错误仍留在当前页面；
4. 401、403、5xx、网络错误分别有可验证的前端行为；
5. 类型检查、定向测试和 staging 真实浏览器验证均有证据。
