# CRM 业务关联与分页需求实现说明

日期：2026-08-26
状态：待本地实现、测试并部署 staging

## 1. 目标

修复 CRM 中“页面展示占位数据”“详情关联为空”“跳转携带 ID 但目标页面不消费筛选条件”等问题，并按既有分页执行参考补齐列表分页能力。

实现顺序固定为：本地代码修改 -> 自动化测试 -> 本地构建/类型检查 -> commit -> 备份 staging -> 部署 staging -> staging 验收。

## 2. 业务功能需求

### 2.1 Account 列表真实指标

Account 列表不得继续使用固定占位值。

- `pipelineAmount`：统计该 Account 关联的开放 Opportunity 金额，排除 `Won` 和 `Lost`。
- `intentScore`：取关联 Opportunity 的最高意愿评分；没有 Opportunity 时返回 0。
- `nextAction` / `nextActionDue`：取开放 Opportunity Action 中最早到期的一条；没有 Action 时为空。
- `risk`：按可解释规则计算：存在逾期开放 Action 为“高风险”；有开放 Opportunity 但没有下一步为“关注”；其余为“稳健”。
- “需求数”：当前 Requirement 数据源为空且没有稳定 canonical 数据，删除 Account 列表中的该展示项；不要用 Demo Request 冒充 Requirement。
- 多币种：当前 DTO 为 number；实现时仅在同币种场景汇总，若后续支持多币种，应扩展为按币种返回，禁止直接相加不同币种。

### 2.2 Contact 360 真实关联

`getContact(contactId)` 必须返回真实关联，不得固定空数组：

- Opportunity：通过 Opportunity Stakeholder 关联联系人。
- Visit：通过 `primary_contact` 关联。
- Demo Request：通过 `primary_contact` 关联。
- Booking：通过 `primary_contact` 关联。
- Timeline：将上述记录按业务日期或 `modified` 倒序合并，类型必须是 `Opportunity`、`Visit`、`Demo Request`、`Booking`，并保留可跳转链接。

所有查询必须继续经过现有权限和客户范围校验，不得因为聚合查询绕过 scope。

### 2.3 Booking 联系人筛选

从 Contact 360 点击 Booking 时，URL 中的 `contactId` 必须生效：

- Booking 页面读取 `route.query.contactId`。
- 后端 Booking 查询支持 `contactId`，并按 `CRM Booking.primary_contact` 精确过滤。
- 同时保留 `accountId`、`status`、`owner`、`source` 等已有/计划中的筛选字段。
- 无匹配记录时显示正常空状态，不回退为全量 Booking。

### 2.4 其他 ID 跳转统一消费

列表页 query 参数统一语义：

- `accountId`、`contactId`、`opportunityId`：严格筛选列表。
- `focus`：保留现有定位/高亮单条记录语义。
- `create=1`：保留现有创建模式语义。

需要修复的入口：

- Lead 转换结果跳转 Account：改为 Account 详情路由，或让 Account 列表消费 `accountId`。
- Lead 转换结果跳转 Opportunity：消费 `opportunityId`，只展示/定位对应 Opportunity。
- Contact 360 -> Booking：消费 `contactId`。
- Opportunity 详情 -> RFQ：RFQ 页面读取并应用 `opportunityId`。
- Contact 厂区链接携带 `siteId`：Account 详情页消费该参数并定位对应厂区；如果无法提供定位，则移除无效 query。

已确认正常的 query 不得回归：Contact -> Opportunity/Demo Request/Visit、Calendar -> Visit/Evaluation、Opportunity -> Quotation、Account -> Installed Tools。

## 3. 分页功能

以 `docs/CRM-功能模块分页执行参考-2026-08-25.md` 为基准实现。

### 3.1 普通列表默认页大小

| 模块 | 默认数量 |
| --- | ---: |
| Account | 10 |
| Contact | 12 |
| Lead | 12 |
| Opportunity 表格 | 12 |
| Demo Request | 10 |
| Demo Test | 6 |
| Demo 档案 | 10 |
| Visit | 10 |
| Booking | 10 |
| Requirement | 12 |
| Quotation | 10 |
| Contract | 10 |
| Installed Tools 档案 | 10 |
| Document 审批 | 6 |
| Document 文件 | 12 |

RFQ 不纳入本次分页改造，但必须支持本需求中的 `opportunityId` 筛选。

### 3.2 公共分页行为

- 支持 `10 / 25 / 50` 每页数量切换。
- 显示总条数、当前页、总页数、上一页、下一页。
- 修改筛选、搜索或每页数量后回到第 1 页。
- 页码、每页数量、筛选条件同步 URL，刷新和前进/后退可恢复。
- 删除当前页最后一条记录后自动回退到上一页。
- 桌面表格和移动端卡片使用同一份分页数据，不能重复请求。

### 3.3 看板规则

- Opportunity、Pipeline：每列初始 5 张，列内独立“加载更多”。
- Installed Tools 生命周期：每列初始 4 张，列内独立“加载更多”。
- 某一列加载更多不得清空或重置其他列。

### 3.4 Dashboard 与详情内嵌列表

- Dashboard 小提醒默认 2 条，大组件最多 5 条，并提供查看全部入口。
- Account/Contact 等详情内嵌列表默认每块 2 条；查看全部跳转到带关联 ID 的列表页。

## 4. 接口与类型要求

- 扩展 `ListQuery` 支持 `accountId`、`contactId`、`opportunityId` 及分页字段。
- Frappe service、Frappe adapter、mock adapter 的筛选行为保持一致。
- Contact detail DTO 的关联数组和 Timeline 类型保持前端现有契约，不引入第二套 DTO。
- 所有列表 API 返回正确 `total/page/pageSize` 元数据。
- 不新增第三方依赖。

## 5. 测试要求

### 后端

- Account 指标：开放商机计入，Won/Lost 排除，最高意愿评分，最早 Action，风险规则。
- Contact 360：四类关联和 Timeline 按联系人返回，权限范围不泄漏。
- Booking：`contactId`、`accountId`、状态和负责人筛选组合。
- 不存在或无权限 ID 返回空结果/标准错误，不返回其他客户数据。

### 前端

- Contact 360 点击四类关联后的 query 正确传递并消费。
- Lead 转换 Account/Opportunity 跳转生效。
- Opportunity -> RFQ 的 `opportunityId` 生效。
- 分页切换、筛选复位、URL 恢复、空页回退。
- mock adapter 与 Frappe adapter 行为一致。
