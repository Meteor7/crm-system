# Notification source boundary

Issues #57, #75 and #51 share one policy: an inbox copy is visible only while its recipient can read the source. List, total, unread count, individual/all read mutations and native DocType reads use the same SQL condition before pagination. Supported source types are an explicit allowlist; recursive Notification sources are not accepted. Document Upload submitters retain service-level access to their own decision messages.

Existing messages with no source, an unsupported source or a deleted source remain stored but are hidden. We do not infer permissions from route strings or backfill guessed sources. New S6 warnings without a historical entry use their actual Opportunity as source; deleting that parent removes its direct inbox copies inside the same transaction. Older child-source history may remain stored but becomes unreadable when the source disappears. Legacy Notification DocShares are removed by permission reconciliation and new independent shares are rejected.

`create_notification` remains strict where a caller reassigns responsibility to a chosen user (Contact owner and Booking owner changes, and the Booking created by an approved internal validation): an assignee who cannot read the source fails the action with `SCOPE_DENIED`. `notify_if_reachable` is used for informational notices (Demo report/status/deadline notices, deadline batches, internal-validation decisions, Quotation/RFQ decision results) and also for workflow announcements addressed to a role or to a participant chosen earlier: Demo submit and approval hand-offs, RFQ revision, approval and reopen notices, internal-validation requests, Document access and upload approval requests, visit meeting notices and Visit/Action assignments. For all of them a disabled user, a user without exactly one CRM role or a user who lost source access is a normal skip: the business state still changes and that user gets no notice. Because of that, a departed assignee no longer blocks a Demo hand-off; checking the assignee up front and returning `INVALID_OWNER` belongs to the business rule that chose them and is a tracked follow-up, not part of this change. Malformed source metadata is rejected before any recipient is skipped, actual persistence failures still raise, and callers keep their transaction/savepoint behavior. In the daily warning job an unreachable recipient is a quiet skip, while a warning row with a missing or unsupported source is written to the Error Log and the batch continues. This is not a catch-all fallback.

A Manager's actual recovery-plan change notifies the current Opportunity owner using the saved revision for deduplication. Initial Created revisions, no-op saves and owner edits do not generate extra notices. Normal unreachable owners are skipped; real notification errors roll back the plan and revision together.

Release requires real Frappe tests for source transfer/deletion, native list/detail, read mutations, DocShare, Demo operations with unreachable recipients and plan-change rollback/deduplication. This document is the intended contract, not evidence those checks have already passed.
